## 1. Reader and IO

- **Header peek is 16 bytes, not 32** (research 4.2). Skipping a `uuid` box never needs its extended type, and a unit test covers the old 16-byte uuid bug. A moof read covers `size + 16`, so the next header is already in the same window.
- **Single read for small files (0.2.0).** A file smaller than the head window plus `perReadMs x bytesPerMs` of the cost model (465,536 bytes by default) is read whole in the first read: by the cost model one read of it costs less than two, whatever the layout. The single read is capped at 1 MiB (`SINGLE_READ_MAX_BYTES`), or at the head window when that is larger, so a cost model with a huge `bytesPerMs` or an infinite value cannot pull a multi-GB file into one buffer; a negative or NaN product leaves the first read at the head window. Every committed fixture now takes 1 read (median 2 before) with identical results; a faststart file in that range reads its remaining bytes too, at most one read's worth by the model. `readMany` serves ranges inside a cached window, so the sidx or mfra prefetch of a small fragmented file reads nothing again.
- **No speculative tail read.** A parallel head and tail read for files above the single-read size was considered for 0.2.0 and not added: it would waste a read on every faststart MP4 and Matroska file above that size, and the moov of a long file does not fit a fixed tail window (2.68 MB on the 3 h file). Instead, after a final `mdat` with no `moov` seen yet, the walk reads the whole remainder when it is at most 16 MiB. Moov-at-end therefore costs 2 reads for any moov up to that size (2.68 MB on the 3 h file). The remainder includes any `free`, `uuid` or vendor box between the mdat and the moov: with an 8 MiB uuid there, a file with a 3.7 KB moov read 8.46 MB of 8.52 MB in 2 reads (real-world probe, section 9). Reading a bounded tail window and walking box headers from there would fix it.
- **Read failures.** A `slice().arrayBuffer()` that rejects or throws, such as `NotReadableError` or `InvalidStateError` after a picked file changed, and a short read become an error with the message `file read failed: <the error as a string>`. Both parsers pass it through as `result.error` (the ISO BMFF parser knows it by that prefix), so it never reads as a corrupt file; an `AbortError` from the source and an aborted signal still reject the call.
- **`readMany` defaults to concurrency 4** (research allows 4-8). It is used only where offsets are known up front: sidx or tfra moof offsets.
- **64-bit values.** Offsets are Numbers. `u64`/`i64` and the box-level `boxU64`/`boxI64` reject values above 2^53-1. In boxes the error is `unsupported: box 'x' at N holds a value above 2^53-1`. In the ISO BMFF parser any other RangeError becomes `corrupt file: ...`. `analyze()` returns every failure as `FileResult.error` and rethrows only an abort.
- **Files above 4 GiB.** Node 24.20 `openAsBlob().size` wraps modulo 2^32, so that test uses a `FileSlice` over `fs.promises.open`. It is opt-in: `FPS_PROBE_LARGE=1`, scratch dir `FPS_PROBE_SCRATCH`, and it is skipped when sparse files are unsupported. Measured on the 4.5 GB co64 file: 4,500,088,814 B logical, 2 reads, 66,712 B, about 6.7 ms. In the browser (built page, Playwright, three picks each, 2026-10-21) the same file gave the same result in 1.8 to 5.6 ms in Chromium 156 and 7 to 10 ms in WebKit 27.2; a manual run, not a committed test.
- **Sniffing** looks at the first 1024 bytes. Unknown content gets `not a recognised container: <reason>`, where the reason names known non-video signatures (PNG, JPEG, GIF, RIFF, Ogg, FLV, MPEG-PS, PDF, ZIP, MP3, plain text).

## 2. ISO BMFF

### Walk and limits

- **moov** is read exactly, up to 256 MiB (`MOOV_HARD_CAP`); above that the result is `unsupported: moov larger than 256 MiB`. The selective moov walk of research 4.2 was not implemented: the 3 h file (648,000 samples, moov 2.6 MB) takes 3.8 ms. When a moov claims to extend past EOF, at most 16 MiB (`MOOV_SUSPECT_CAP`) are parsed and a warning is added, as ffprobe recovers such files too.
- `mehd` is not read, as in ffprobe, so an all-ones (unknown) fragment duration cannot fail a file. Nor does an all-ones version 1 duration in `mvhd` or `tkhd`, which the analysis does not use, or in `mdhd`, which reads as 0 as in ffprobe 8.1.1: a stream duration of 0 and no format duration, with the frames and rates of the sample tables, checked against ffprobe on patched copies of `cfr_h264_30.mp4`. A second moov is ignored with a warning. A moof before moov, a moof above 64 MiB and a missing moov are errors. Garbage after moov stops the walk with a warning. So does a top-level header after moov that runs past the end of the file, whatever its type, unless it is an `mdat` or a `moof`, which hold samples and are truncated boxes: it is trailing data (`ignored trailing data at N: not a box`), such as the trailer of some phone MOV files, which ffprobe 8.1.1 reads without a word. The file still counts as cut, so a sample that lies past the end is dropped with a truncation warning on its track. A box type is read with every byte outside printable ASCII as `?`, so no warning, error or `fourccOrCodecId` carries a control character from the file. The walk also stops with a warning after 4,000,000 top-level boxes; 2M tiny boxes take 1.2 s and 246 reads.
- **Entry tables** (stts, ctts, stss, trun) are bounded by their box size and an overrun is recorded. An overrun turns off ffprobe equivalence for that table, because 8.1.1 reads past the box.
- **stts** ports `max_stts_delta` (deltas above 4294487295 become 1, with the mov.c drift correction). **ctts** offsets are signed 32-bit in both versions.
- **Fragment read-ahead** follows research 4.2 (1 MiB when the next mdat is at most 64 KiB, else `clamp(2 x moof + 64, 1 KiB, 64 KiB)`).
- **Prefetch hints** come from a top-level sidx with more than one subsegment, or from mfra/tfra. Only fragments with mdat above 64 KiB use them, in batches of 8 ranges at concurrency 4. The mfra path runs only when no sidx hints exist and more than 16 fragments remain; it costs one 64 KiB tail read. Hints must never change a result:
  - mfra parsing never throws (abort excepted);
  - tfra offsets that are 0, beyond EOF or above 2^53 are skipped;
  - hints are dropped after the first window that does not start with moof, styp, sidx, ssix, emsg, prft, free, skip or uuid.

  Stale tfra offsets (+100) cost 40 reads against 35 without hints.
- **trun** with no per-sample fields claims `count` samples from 12-20 bytes. Zero-size record-less samples are capped by the bytes left in the file. One crafted file went from 33.5M frames in 2.7 s to 142 frames in 11 ms.

### ffprobe emulation

- **Two averages.** `avgFps` is the full-file truth. `avgFpsFfprobe` emulates the 8.1.1 header phase and is what the compare script checks.
- **Header extent** is research 2.1 plus these conditions. A sidx counts as complete only when it is non-hierarchical, has `first_offset` 0, references an existing track and ends at EOF or at EOF minus the mfra size (the last 4 bytes are read only when needed). A sidx cut by EOF is ignored. A truncated sidx header is an error, as in ffprobe.
- **`ffprobeReject`.** 8.1.1 resets `found_tfhd` per moof, not per traf, so a missing trex, `tfhd` track_ID 0 or an unknown track makes it fail with `error reading header`, and a traf without trex after a valid one is read as another track. When the offending moof lies inside the ffprobe extent, every track gets `avgFpsFfprobe` and `rFpsFfprobe` null plus a file warning. The truth values are kept. Outside the ffprobe extent a missing trex only adds `no trex: sample defaults taken from tfhd`.
- **`avgFpsFfprobe` is null** (never `0/0`) when N or D is 0 (ffprobe fills the value from packets), when stts or a visible trun overran its box, or on `ffprobeReject`. The UI shows the ffprobe string only when it is not null.
- **`rFpsFfprobe` is stage 1 only** and a port of `mov_merge_tts_data` and `mov_fix_index` (n8.1.1):
  - Without ctts, the kept durations are `stts[0..retained)`, continuing across edits, because `tts_index_old` is not repositioned. With ctts they start at the found index.
  - The rate is constant when every kept duration except the last equals the first.
  - It is null when the edit list has no media edit, for pure fragmented files, when a table overran its box, for a rejected file and for a broken track. A uniform stts plus at least one media edit gives that delta.
  - Work is lazy and bounded: run-length tables, an stss key list and binary searches, with a 2,000,000-step limit (or `maxExpandedSamples` if lower) when ctts forces a keyframe walk. At the limit it returns null with `r_frame_rate not reproduced: edit list walk limit reached`.
  - Why: the first version collected durations into arrays. A 12.6 KB file with 1000 elst entries and a VFR stts took 249 MB of heap and died with a fatal OOM at a 256 MB limit. Now it takes 12 ms with no RSS growth; 10,000 edits over 100,000 samples take 26 ms; a 599-byte file with 10M samples takes 9 ms; ctts with 20,000 edits over 1M samples takes 101 ms and reports not reproduced.
  - A sweep of 27 edit windows over each of three VFR fixtures (81 cases): 0 mismatches against ffprobe, 4 agreements, the rest null.

### Tracks and timing

- **Which traks are video.** Handler `vide` in `mdia/hdlr`, or any non-`soun` handler whose sample entry (the original format for encv/sinf) is a known video fourcc. Chapter-referenced traks (`tref chap`) are never video. **`auxv` is kept as video**: ffprobe 8.1.1 lists it and counts it in format duration. It gets a warning and a lower primary score.
- **Primary track score:** enabled with more than 1 sample = 2, disabled with more than 1 sample = 1, `auxv` = 0.5, still = 0; higher wins, then more frames, then file order. The last step gives `expect=still` files a primary whose `isStill` is true. Stills keep the ffprobe-equal `avgFps`, `avgFpsFfprobe` and `rFpsFfprobe`; min, max and VFR are null.
- **Duplicate track_IDs.** The first track keeps its id (as ffmpeg's fragment mapping does); later ones are reported as max id + 1, +2, ... with track and file warnings. Without this `primaryTrack()` resolved to the wrong track.
- **Broken tracks** (ffmpeg `sanity_checks`: chunks without stts/stsc/sizes, or sample count without chunks) stay in `videoTracks` because ffprobe lists them. They get null duration and start, `presentedFrames` 0 and no stats; in format duration they add only their mdhd duration at 1/90000.
- **elst.** The declared count is trusted only if it fills the box exactly, otherwise `box size / entry size` is used. A later non-empty elst replaces the earlier one (`duplicated elst: the last one is used`). A version 1 segment duration of 0xFFFFFFFFFFFFFFFF means unknown: a media edit lasts from its media_time to the end of the media, the composition time of the first sample plus the sample durations (`unknown elst duration: the edit lasts to the end`), so an edit that trims the start keeps the trimmed duration: `mp4_elst_trim_start.mp4` patched that way still presents 69 of its 90 frames over 2.303 s, with a format duration of 2.303 s, and an empty edit is ignored (`unknown elst duration: the empty edit is ignored`), so it does not delay the track by 2^53 ticks. ffprobe 8.1.1 fails such a file (`Invalid edit list duration=-1`), so it is an `ffprobeReject` and both ffprobe rates are null; any other value above 2^53-1 is still `unsupported`. Presented frames follow the first non-empty edit only, with a warning when more exist. For fragmented tracks the media_time start is applied and the end is not, because ffmpeg never discards fragment samples by edit list. The window is dropped when it provably covers every sample (no ctts, no fragments), a speed shortcut.
- **Format duration** is a port of `update_stream_timings` over audio and video in integer microseconds; text and data tracks count when they extend it by less than 1 s.
- **`frames`.** Non-fragmented: the stts sum (`nb_frames`), capped at the stsz count with a warning when they disagree. Fragmented: moov samples plus present trun samples. `presentedFrames` is the timeline count inside the edit window.
- **Several sample descriptions.** Codec and size come from the first stsd entry, with the warning `N sample descriptions, first used`; frames and rates come from stts and the fragments, whichever description a sample points to. ffmpeg also takes the codec from the first entry; for size ffprobe prints what it decodes, the first entry's on `mp4_stsd_two_entries.mp4`, whose second entry claims 320x180 for the second half of the samples. An entry whose size differs from the SPS keeps its stored size: the SPS crop is not read.
- **Codecs.** About 40 common fourccs from `isom_tags.c`; the esds object type remaps `mp4v` (mpeg4 or mjpeg); `dvh1` with hvcC is handled; anything else is `unknown`. The AVI bmp-tag fallback is not ported.
- **Rotation** is tkhd x mvhd, `-atan2` truncated like ffprobe's `print_int`. It matched ffprobe in 27 of 27 matrix combinations.

### Truncated files

- Non-fragmented: `frames` stays the stts sum, but `presentedFrames` and the statistics use only complete samples, counted from stsc/stco/co64/stsz/stz2 (53 of 90, the ffprobe value). Average and duration stay header based, as in ffprobe. Only then are the chunk and size tables walked.
- Fragmented: `frames` counts samples whose data starts before EOF (73, equal to `nb_read_packets`); presented counts complete samples (72, equal to `nb_read_frames`).
- The build phase after the walk runs inside the same error handler as the walk, so any out-of-bounds read becomes a `corrupt file: ...` result.

## 3. Matroska

- **Primary track** is the first TrackType 1 entry. `trackId` is the TrackNumber. Audio-only files return `error: null`, no tracks and the warning `no video track`.
- **Modes.** `header` reads only the head window and Stage A; `probe` adds sampled blocks; `exact` walks every block; `auto` picks exact or probe from a cost prediction. `scan` records the depth reached. Below the single-read size (section 1) the first read is the whole file in every mode, so the mode then changes the parsing work, not the bytes read.
- **Header (Stage A).** Budget is 5 reads and 1 MiB, checked against bytes already fetched plus the next read, including the Segment search. It follows SeekHead (and a chained one) for Info, Tracks and Tags.
  - Resync: only level-1 IDs, Void and CRC-32 are accepted. Anything else triggers a search from just after the last good element. An element that claims to end beyond EOF is parsed as far as it goes. A damaged Segment ID falls back to the first valid level-1 element. A Segment size above 2^53 or too small is read to EOF with a warning. Cluster discovery falls back to up to 4 Cues positions.
  - A Tracks element above the cap is read entry by entry, skipping children above 64 KiB such as CodecPrivate.
  - `parseMaster` has an allowed-children table per parent and a nesting limit of 16 (ffmpeg's `EBML_MAX_DEPTH`). Before this, 3000 nested SimpleTags overflowed the stack. A TrackEntry outside Tracks is ignored.
  - Tags: Targets and DURATION are collected per Tag and matched after the Tag is read, so element order does not matter. Only a SimpleTag directly under a Tag counts. The UID is a BigInt.
  - A Video FrameRate substitutes a missing DefaultDuration, with a warning.
  - Strings (CodecID, DocType, tag names and values, attachment MIME types) are decoded as UTF-8 up to the first NUL, with every other control character replaced by `?`, so no warning carries one.
- **Timestamps** follow ffmpeg: ticks are `cluster / TrackTimestampScale + relative - CodecDelay` in the track time base `trunc(TimestampScale x TrackTimestampScale) / 1e9` (this corrects research 2.2). Blocks before time 0 have no PTS in ffmpeg; the scan fills them from the neighbouring frames the way libavformat does and counts them. Codecs with B-frames may differ there.
- **Durations.** BlockDuration, else `DefaultDuration x laces / TimestampScale` with integer division, else the median delta (research 4.5). Where the file stores no duration for the last frame, the measured average differs from ffprobe's by that rule; the compare scores it within-tol (sections 7 and 9).
- **Exact scan recovery** is a port of how ffmpeg 8.1.1 recovers, which the first version lacked (one flipped bit gave 6 frames instead of 235):
  - it remembers the last good element, and after any error searches again from just after it, backwards if needed;
  - children are checked against their parent's end, so a block that overruns its Cluster drops the rest of that Cluster;
  - Cluster and BlockGroup have fixed allowed-children lists, and unknown IDs are skipped by size without counting as good;
  - after any error the Segment is treated as unknown-size, so data past its declared end is read;
  - `truncated` is reported only when the error was running into EOF and nothing valid follows;
  - it is stricter than ffmpeg in one place: a Cluster found by resync must have a Timestamp child, and other level-1 elements must fit in the file and start with a valid first child;
  - resync warnings are capped at 5, then one `N more` line.
- **Block validation** as in ffmpeg: the track number must exist in Tracks, at least 3 bytes must follow it, fixed, Xiph and EBML lacing are validated (EBML lace sizes with BigInt), a Timestamp, BlockDuration, ReferenceBlock or DiscardPadding above 8 bytes is invalid, and so is a block above 256 MiB.
- **Concatenated files.** A second Segment, or data after a known-size Segment, is counted like ffprobe does, with a warning (a file concatenated with itself: 180 frames).
- **Duration values.** An Info Duration of 0, or of 0 bytes, means absent (N/A). A negative Duration is kept (ffprobe prints -5.000000). NaN or Infinity gives `invalid Duration value`. A false Info Duration is kept in `formatDurationSec` exactly like ffprobe (10.0 for a 3.0 s pipe recording) and the scan reports the real span with a warning.
- **Cost model for `auto`.**
  - The block density of all tracks is sampled from up to 16 KiB at the first Cluster. The first version divided all bytes by video frames only, so interleaved audio inflated the frame size and a slideshow with Opus ran exact with 1429 reads (about 1155 ms) against 8 reads (20.9 ms) now.
  - Both plans are computed with the research cost formula and the cheaper wins: 4 KiB windows (reads = large blocks + small bytes / 4 KiB) or 1 MiB windows. Under the default model 4 KiB wins only above about 290 KB per frame, not at 32 KiB as research 4.5 says.
  - A CPU term was added: `perBlockMs` 0.0002 in `CostModel` (measured about 0.18 us per block in Node). Without it a 648,000-block file was predicted at 40.9 ms and took 116-170 ms; now it is predicted at 172 ms and runs probe. It needs browser tuning.
  - Exact runs when the prediction is at most `exactBudgetMs` (150 ms), plus, for a first video track without DefaultDuration whose ffprobe estimate can run, the predicted cost of the walk that probe mode reads for that estimate: 48 video packets at the bytes per video packet of the density sample (at most 5,000,000 bytes and the region) in reads of the head window. Probe mode pays that walk anyway, so the budget is what exact may cost on top of it. If 4 KiB windows need more than `2 x planned + 16` reads the scan switches to 1 MiB windows. A false small Duration can only raise the block estimate, never shrink it (the earlier plan trusted a 1 ms Duration and ran exact with 3449 reads).
- **Probe** samples 8 clusters x 32 video blocks (from Cues, always including the first cluster, or by validated sync search) and merges per-run deltas with the shared VFR rule. A tail scan reads 256 KiB growing x4 up to 16 MiB and steps back to the last video block. Probe output is `sampled` and never contains an average or a frame count. A frame estimate appears only as a warning (`assumes CFR`).
- **Provenance.** `frames` and `presentedFrames` are `computed` after an exact scan. The exact average is `frames / span` (an exact rational through `avgFrameRate` when some frames have no PTS). `nominalFps` is `declared` when DefaultDuration exists, else the timeline's exact or snapped rate after a scan. Header mode leaves min, max and VFR null.
- Image attachments are counted in a warning, never listed as tracks.

### ffprobe frame rates without DefaultDuration (0.2.0)

Without a DefaultDuration (and without a Video FrameRate, which stands in for one) ffprobe prints an `avg_frame_rate` and an `r_frame_rate` that it estimates from the first packets while it opens the file. `src/core/rfps.ts` reproduces both for `avgFpsFfprobe` and `rFpsFfprobe`. It is a lazy chunk that the Matroska parser imports only for such a track, in `probe`, `exact` and `auto` mode; `header` mode reads no block, so both stay null there with a warning. The algorithm is re-implemented from its description in the FFmpeg n8.1.1 sources (LGPL); no FFmpeg code is copied. The functions named below are where each step lives:

- **Time base and timestamps.** The stream time base is `TimestampScale x TrackTimestampScale / 1e9`, reduced (`libavformat/matroskadec.c`, `matroska_parse_tracks` through `avpriv_set_pts_info`). A packet's pts is the absolute block timestamp in that time base, `cluster / TrackTimestampScale + relative - CodecDelay` (`matroska_parse_block`), never rebased to 0. Packets come in file order, every track's blocks included. A DefaultDuration in the 5 to 1000 fps range sets both rates in `mkv_parse_video` instead, which is the declared path of the parser.
- **Packet durations.** BlockDuration, else `DefaultDuration x laces / TimestampScale` (`matroska_parse_block`). An Opus packet without either gets its parser's duration, the TOC frame count times the frame length, rescaled from 48 kHz to the time base rounding down (`libavcodec/opus/parser.c`, `set_frame_duration`; `libavformat/demux.c`, `parse_packet`). A video packet without either gets 1 tick when the time base is coarser than 1 ms and none otherwise (`demux.c`, `compute_frame_duration`, while `r_frame_rate` is still unset).
- **Track and format durations.** ffprobe prints no stream duration for a Matroska video track, only `format.duration`: the Info Duration (`matroska_read_header` scales `duration` by `TimestampScale`), else its estimate. `durationSec` is the measured span, from the first block to the last one plus the duration the demuxer gives it (`matroska_parse_block`: BlockDuration, else `DefaultDuration x laces / TimestampScale` in integer arithmetic, so a 60 fps DefaultDuration of 16666666 ns lasts 16 ms on 1 ms ticks; with neither, the median interval, by design). The muxer that wrote the Info Duration ended the same frame at its own rounded duration, so the two differ by up to one frame: `vfr_screenrec_ts1000.webm` spans 5.999 s against an Info Duration of 6.000, and a MediaRecorder file whose Duration sits at its last timestamp is shorter than its span. `formatDurationSec` equals ffprobe's on every fixture, and `check` judges it instead of the span when the two, rounded to the microsecond, are within one typical frame interval: that of `dominantFps`, else of `nominalFps` on a constant track, else the average one. The result holds no median interval, and the Chromium recordings, whose intervals are mostly 16 or 17 ms with gaps of up to 0.7 s, have no dominant rate, so their average interval of 27 ms stands in for their median of 17 ms; their format duration is 16 to 17 ms off the span. 1 / `minFps`, the longest interval, would take any format duration of `late_freeze_10s.mkv` within 10.04 s.
- **Decoding timestamps.** VP8, VP9 and AV1 have no decoder delay, so dts is pts (`demux.c`, `compute_pkt_fields`). H.264 has no dts until 7 frames are decoded (`has_decode_delay_been_guessed`), then its pts (`select_from_pts_buffer` with no reorder delay): the first 7 packets count as packets but carry no timestamp into the estimate. That holds while the decoder keeps a reorder delay of 0 and outputs a frame for every packet, which the headers prove in two ways. A VUI `bitstream_restriction` with `max_num_reorder_frames` 0 fixes the delay (`has_b_frames` 0, never raised), but then a picture whose POC is below the last one output is not output at all (`h264_select_output_frame`: `out_of_order` with no reorder buffer, logged as `no picture ooo`; only an IDR or an MMCO reset restarts the order), so the decoder sees one more packet before 7 frames and its dts start a packet later; the estimate therefore reads the slice headers of the 7 packets and requires the POC never to go back after the IDR and no `frame_num` gap (a gap makes FFmpeg insert frames it does not output and clear its POC history), while a step forward of any size, or a repeated POC, is output in order. Without one, the decoder raises the delay to 1 when the picture order count of a decoded frame steps by more than 2 or goes back (`libavcodec/h264_slice.c`, `h264_select_output_frame`), so the estimate reads the slice headers of the 7 packets the decoder sees, computes their POC as the standard does for `pic_order_cnt_type` 0 (`pic_order_cnt_lsb`, its msb from the last reference picture, reset at an IDR) and 2 (from `frame_num`, one below for a non-reference picture), and requires every step to be 1 or 2. Both ways also require the first packet to be an IDR: FFmpeg outputs no frame for a first I slice that is not one (`ffprobe -count_frames` gives 149 frames for 150 packets on such a file), so its decoder sees 8 packets before 7 frames and its dts start one packet later, which the estimate does not model.
- **The analysis loop** of `avformat_find_stream_info` (`demux.c`) with ffprobe's defaults (`libavformat/options_table.h`: probesize 5,000,000 bytes, analyzeduration 0, which becomes 5 s, fpsprobesize -1, max_ts_probe 50). Before each packet it stops when every stream is done: the video stream has decoded a packet and holds `fps_analyze_framecount` intervals (40 when the time base is coarser than 0.5 ms, else 20, and 0 when `tb_unreliable` is false), and every stream has a timestamp or 50 packets. It also stops before a packet once the packet payloads read reach the probesize, and at EOF. After reading a packet of a stream that already has two, the stream's analysis time, its summed packet durations or, with none after 30 packets, its dts span, stops the loop at 5 s without counting the packet. An Opus track therefore keeps the loop reading until its first block, and can stop it after 5 s of audio.
- **Interval statistics** (`demux.c`, `ff_rfps_add_frame`): for every video dts above the previous one, the absolute time is compared with the grid of each of the 399 standard rates of `get_std_framerate` (n/12 fps up to 30 fps, whole rates up to 60, then 80, 120, 240 and the six x/1.001 rates) at offsets 0 and 0.5, and the errors and their squares are summed. Every 10 intervals a rate whose variance exceeds 0.04 at both offsets is dropped. The gcd of the intervals starts at the fourth. `tb_unreliable` is true for H.264 and for a time base of 1/101 s or finer, or coarser than 1/5 s.
- **Rates** (`demux.c`, `ff_rfps_calculate`, then the end of `avformat_find_stream_info`): `r_frame_rate` is the time base over the gcd when the gcd exceeds `max(1, 1/(500 x time base))` after more than 15 intervals, else the standard rate with the smallest variance below 0.01, kept only if it is below 1.01 times the time base rate; `avg_frame_rate` is that rate when no packet carried a duration and the mean interval is within one tick of it. Otherwise, when packets carried durations, `avg_frame_rate` is frames over their summed duration, snapped to a standard rate within 1%. A rate still unset becomes `1/time base` for `r_frame_rate` and `0/0` for `avg_frame_rate`. All of it runs in IEEE doubles in FFmpeg's evaluation order, with `llrint`'s ties to even, so near ties resolve as in the gyan.dev 8.1.1 x86-64 build.
- **Reads.** The estimate takes the blocks of the Clusters from the first, in file order, through the scanner's block hook: block headers, each Opus TOC byte and the head of the first video block (of the first 7 for H.264), for the SPS, the PPS, the slice headers or the AV1 sequence header. It copies those heads from the scanner's buffer and, after the walk, reads one again (at most 1 KiB) when the buffer did not hold it, before the codec check, so also when the SPS in CodecPrivate then rules the estimate out. In `exact` mode, and in `auto` when it picks exact, the hook of the exact scan feeds the estimate until it has what ffprobe reads, so the first Clusters are read once and the exact plan of `auto` covers the estimate except those head reads, which it does not count (on synthetic H.264 files with 100 to 250 KB frames one size in 378 needed one, with 1 MiB windows; with 4 KiB windows and 5 to 60 KB frames none did); before 0.2.0 the estimate walked them first with its own reads (a 20 MB 720p60 VP8 WebM without DefaultDuration: 26 reads, now 20, for the same 19.9 MB and the same strings). In `probe` mode it walks the first Clusters itself, before the probe, because the probe reads at most 32 blocks of the first Cluster; that walk is bounded by the limits below, and `auto` counts its predicted cost when it picks a mode. On a 149.1 MB 720p60 VP8 WebM without DefaultDuration (150 s at 8 Mbit/s, generated with ffmpeg and not committed) probe mode reads 72 times and 4.72 MB, against 63 reads and 4.59 MB for the same file with DefaultDuration, so the walk costs 9 reads and 131.5 KB (7.5 ms in the cost model; the plan predicts 10 ms for it). `auto` still picks probe there, since exact is predicted at 415 ms (142 reads, 147.9 MB, 211 ms measured in Node). A Chromium recording stops after 41 video packets, 48 for H.264. The walk ends once 5,000,000 bytes of packets are read or a stream's summed packet durations reach 5 s, but a stream without durations has its dts span held against 5 s only from its 31st packet on: a 2 fps track without BlockDurations is read for 31 packets, about 15 s of media (a 1 fps track for 30 s), and the same track with BlockDurations for 12.
- **Verified.** The 12 committed files without DefaultDuration (the 8 Chromium WebM and Matroska recordings, `vfr_concat_10_30_60.webm`, `vfr_two_phase_5_200.webm`, `late_25_to_12.5.webm` and `vp9_no_defaultduration.webm`) give ffprobe's strings in probe, exact and auto mode (`tests/matroska/rfps.test.ts`), and the compare scores them exact. Outside the corpus, 7 more Chromium recordings, 376 files rebuilt from the recordings' frames with random timing (constant rates from 2 to 240 fps, jitter, duplicates, rate changes, gaps, BlockDurations, TimestampScale from 1e5 to 1e7 and 1001000) and 120 files with an Opus track that starts up to seconds late, all without DefaultDuration, matched ffprobe 8.1.1 on both strings in probe and exact mode. Those files were generated and checked on the maintainer machine and are not committed.
- **Not reproduced** (both fields null, and the warning names the reason): header mode; more than one video track, attached pictures, duplicate track numbers, a TrackTimestampScale other than 1 or ContentEncodings; a codec other than VP8, VP9, AV1 and H.264; any other track than Opus with channel mapping family 0 (subtitles, Vorbis, AAC, PCM); laced blocks or blocks before time 0 among the analysed packets, an invalid Opus TOC, a first video SimpleBlock that is not a keyframe, damaged first Clusters; H.264 other than Baseline, or whose SPS (CodecPrivate, else the first block) has VUI timing info, HRD parameters, a pic_struct flag or frame reordering, or whose first packet is not an IDR; H.264 whose first 7 packets give a POC step other than 1 or 2 (without `bitstream_restriction`) or a POC that goes back (with it), a `frame_num` gap, `pic_order_cnt_type` 1, field coding, a bottom field POC offset in the PPS, or a slice header that cannot be read in the first 1024 bytes of a packet; AV1 whose sequence header (CodecPrivate, else the first block) has timing info, or no sequence header. These are the cases where ffprobe's result depends on a codec frame rate, a decoder delay or packets the walk does not model.
- **Assumptions left.** From the IDR on, each of the first 7 H.264 packets is assumed to decode one frame; a packet that decodes none would shift the dts as a first slice that is not an IDR does, and the estimate would differ from ffprobe's. On 128 Baseline Matroska files built for this check (x264 output without the VUI, its POC kept at `pic_order_cnt_type` 2 or rewritten to type 0 in steps of 2 or 4, with random timing, BlockDurations or dropped frames), the parser gave an estimate for 67, each equal to ffprobe 8.1.1's strings, and none for 61. ffprobe printed `Increasing reorder buffer to 1` for every file with steps of 4, and its strings then differed from a delay-0 estimate on 3 of the 4 files with BlockDurations but on none of the 35 without; a dropped frame did not raise the delay, because FFmpeg conceals the missing `frame_num`. The parser does not model either effect, so both stay not reproduced. On 240 more such files whose first packet is an I slice that is not an IDR (no VUI, or `bitstream_restriction` without reordering), the parser without the IDR rule gave 166 estimates, 5 of them different from ffprobe 8.1.1's strings, and it now gives none; on 320 files that start with an IDR it gives the same 235 estimates as before, each equal to ffprobe's. Those files were generated on the maintainer machine and are not committed. Another FFmpeg build with FMA contraction or x87 arithmetic could flip a near tie between two rates (the closest one in the corpus: 59.94 fps at a variance of 0.003162 against 60 fps at 0.003384, `rec_chromium_vp8.webm`). Timestamps above 2^53 ticks lose precision. A DefaultDuration outside 5 to 1000 fps keeps its declared `avg_frame_rate`; ffprobe then estimates `r_frame_rate` from packets, which is not modelled, so `rFpsFfprobe` stays null.

## 4. Statistics and VFR

`src/core/stats.ts` follows research 4.3. Deviations and details:

- **Tail exclusion.** The last `1 + reorderDepth` deltas are dropped, but all deltas are kept when fewer than 2 would remain. On very short tracks the reference data (`ref-extract.mjs`) drops `min(positive deltas, 1 + reorderDepth)` and reports no min or max; no fixture hits the difference.
- **Median** is the lower median by cumulative count. VFR is any remaining delta farther than `max(1 tick, round(0.5% x median), 1 ms)`, where the 1 ms term counts only when the timescale is above 1000 and every kept delta is a whole number of milliseconds (`msGridTicks`). That term makes an MKV-to-MP4 remux (timescale 16000, 8 and 9 ms deltas) CFR, 1 ms quantized, like its source; `ref-extract.mjs` uses the same rule. `dominantFps` is set only for VFR tracks where the most common delta covers at least 50% of the frames.
- **Nominal rate.** One distinct delta gives an exact rate. A CFR track with two or more distinct deltas snaps the mean of the kept deltas (not the full average, whose odd last tick moved 240 fps at timescale 600 to 240000/1001) to {24, 30, 48, 60, 120, 240} x 1000/1001 or an integer 1..240 within 0.1%. `timestampsQuantized` marks CFR with quantized ticks (Matroska 1 ms, and the millisecond grid above).
- **Presented average.** `presentedAvgFps` = presented frames x timescale / (last PTS + stored duration of the last presented sample - first PTS); a zero stored duration falls back to the median delta. ISO BMFF reports it as `avgFps` (provenance exact) and keeps the duration-sum rational in `avgFpsFfprobe`, so the average agrees with Frames and Duration when an edit list trims VFR samples, a fragment is lost or overlaps (Chrome MediaRecorder `tfdt`), or the first frame is held. The library engines use the same value through `applyStats`.
- **Held last frame.** When the stored duration of the last presented sample is at least 0.5 s and 4 median deltas (MP4 stts or trun, Matroska BlockDuration), a warning says so, because the average then sits below the frame rate.
- **Profile gate.** The rate profile job is created when the largest delta is more than 7.5% above the smallest, unless the VFR rule calls the track CFR and the spread is within the VFR tolerance and below 2x (timestamp rounding only). CFR fixtures therefore never load the segments chunk, including 120 and 240 fps WebM at 1 ms ticks.
- **Odd TimestampScale.** A Matroska timescale of 1e9 / TimestampScale that is not an integer is turned back into nanosecond ticks, so min, max and the average stay exact rationals (`10000000/333333` instead of `3000003/100000`).
- **Fast path.** With constant ctts, no discontinuities and no negative durations, stats are computed from stts runs in O(runs). Otherwise a `Float64Array` of PTS is built, refused above 5M samples (`per-sample analysis skipped`; it was 50M, which let a 190 KB MP4 allocate 382 MB). The Matroska PTS array grows only up to the same limit, and the exact-scan cost model counts laced frames, not blocks.
- **PTS input** (Matroska) takes `lastDuration`; reorder depth comes from the `ctsRange` or, when absent, from the largest PTS lag.
- **Cost.** On the 1 h VFR file (124,761 stts runs) stats dominate the 21 ms total because the run generator is walked 2-4 times; plain index loops should roughly halve it. This is a performance note, not a correctness issue.
- `avgFrameRate(ts, N, D)` uses BigInt and a port of `av_reduce` (`807689923/26949920` and `19001/317` are unit tests).

## 5. Comparison engines

All engines return `FileResult` and fill the shared fields from `analyzeTimeline`, so mp4box and mediabunny are measured as parsers, not as timelines. They import only `core/{types,reader,rational,result,sniff,stats,options}`, never `analyze.ts` or `core/index.ts`, so no own parser is bundled with them. Native library values go into track warnings (`mp4box native: ...`, `mediabunny native: ...`) and into `result.mp4box` / `result.mediabunny`.

### mp4box 2.4.1

- **Feeding.** A `BlobReader` over a `CountingBlob` walks the top level and feeds ftyp, moov, sidx and other boxes whole, each mdat as a 16-byte header only (mp4box needs a contiguous stream to jump over it), and each moof plus the next mdat header. It stops after moov when there is no mvex. A naive append loop reads 100% of the file. Cost: 1 read (faststart) or 2 reads, fragmented 2-3 reads (96-131 KB), the 3 h file 3 reads and 2.68 MB in 214-313 ms.
- `Log.error` is replaced once (a global side effect) because mp4box prints with `console.error` and has no switch; messages become `mp4box log: ...` warnings.
- **Native pitfalls**, recorded per track:
  - the last sample duration is overridden to `mdhd.duration - last dts` (fires on 2 of 65 tracks; last 3003 vs stts 1001, 29.32 fps against 29.97 true);
  - fps from sample durations is off by more than 1e-6 on 4 tracks, from mdhd duration on 3, from movie duration on 10 (hybrid fragmented: 119.88 vs 29.97);
  - the ProRes sample entry is not parsed (dimensions fall back to tkhd);
  - a corrupt stts count raises a RangeError, turned into an error result.
- Matroska input returns the error `unsupported by mp4box` after one read.

### mediabunny 1.62.0

- **Source.** `CustomSource` (the `StreamSource` alias is deprecated) with `prefetchProfile: 'fileSystem'` like `BlobSource`, over `CountingBlob`. Formats are MP4, QTFF, WEBM and MATROSKA only. A read that rejects, throws or comes back short becomes `file read failed: ...`, as in the own reader, so a picked file that changed since is neither `not a recognised container` nor the browser's bare message. It is `result.error` wherever it happens, also in the packet walk of a track, where any other error drops only that track, with a `track N: ...` warning. `Logging.level` is set to Silent (global) and log lines become `mediabunny log: ...` warnings.
- **Packet walk.** `sink.packets()` (also used inside `computePacketStats`) stalls about 90 s once a metadata-only walk passes roughly 500k packets (profiled to `timestamps.shift()` on a huge array in `media-sink.js`). The engine walks with `getFirstPacket`/`getNextPacket` (648,000 packets in 0.75 s) and calls the real `computePacketStats()` only for tracks up to 150,000 packets. Above that it applies the same formula to its own pass and says so in a warning.
- **Fields.** `avgFps` and `avgFpsFfprobe` hold the native `averagePacketRate` turned into a rational by a continued fraction, so CFR gives exact rationals while 1 ms WebM stays visibly off. Min, max, VFR, duplicates and frames come from `analyzeTimeline` in PTS mode on tick-rounded timestamps. The native stats pass is excluded from `io` and reported as `nativeStatsMs`. `brand` is null. The rotation sign mapping is untested (no rotated fixture).
- **Library gaps** found: `vp9_unknown_clusters.webm` yields 0 packets silently; the adapter counts the packets an edit list trims, which mediabunny gives negative timestamps (`mp4_elst_trim_start` presented 90 vs 69); hybrid fMP4 sees only moov samples (30 vs 120); a truncated fragment gives 90 vs 73; a truncated no-moov file exposes zero tracks without an error (the engine adds a warning); mp4v and mjpeg both read as mpeg4. Cost: 1 read on small files; whole clusters for Matroska; 3 h file 3 reads, 2.87 MB, 749-872 ms.

### rVFC (main thread, Chrome 155 only)

- **Contract.** `estimateWithRvfc(file, { host, signal, onProgress })`. The host element must be attached, visible and in a foreground tab, or no frames are presented; a hidden tab gives an error instead of a hang (1.5 s refresh probe, 6 s guard per pass, 8 s metadata timeout). `container` is always `unknown`, `io` is `{0, 0, ms}`, every value is `estimated` and the first warning is `approximate: estimated by playback`. The object URL and element are always released.
- **Passes.** Pass 1 runs at rate 1. Later passes continue playback with `currentTime = 0` and a halved `playbackRate`, without waiting for `seeked`. The first 3 callbacks are skipped, and only pairs whose `presentedFrames` advanced by exactly 1 count. A pass is accepted when `fps x rate <= 0.51 x refresh` and it is the first pass, shows variable intervals, or agrees with the previous pass within 0.3%. At most 5 passes, so 240 fps needs 5 passes (9.3 s on the 33 Hz default headless display).
- **Estimates.** `fps` is the median of the deltas in and next to the most common log-scale bin; `avg` is presented frames over media time. `spread` is the share of deltas more than `max(5%, 1.2 ms)` from the typical one, and above 2% the clip is flagged `vfr`. Snapping uses 24/25/30/48/50/60/100/120/144/240 plus the x1000/1001 variants of multiples of 6, tried on the typical delta, then on the average.
- **Confidence.** Flags are `few-samples` (under 20 pairs), `passes-differ`, `display-limited`, `vfr`, `estimates-differ` and `non-standard`. Zero flags is high, one is medium, two or more low.
- **Measured** (throwaway headless profile): H.264 CFR at 23.976, 25, 29.97, 30, 60, 120 and 240 fps all snapped to the exact ffprobe rate. At 60 Hz, 30 fps took 1.87 s in one pass, 60 fps 3.4 s, 120 fps 4.9 s. WebM 1 ms timestamps cannot separate 29.97 from 30, so 30 fps content came out as 30000/1001 on the 33 Hz regime (30/1 at 60 Hz) with `estimates-differ` and medium confidence. VFR files were flagged `vfr`, `passes-differ`, `estimates-differ` with low confidence. HEVC in headless Chrome, ProRes, audio-only and garbage give clear errors. Node tests use a simulated display and fake timers (single pass, NTSC snapping, aliasing with adaptive halving, confirming pass, quantized timestamps, VFR early stop, short clip, restart of a short clip, unplayable codec, hidden tab, missing API, abort).

## 6. UI and worker

> Historical: this section describes the app before the package (2026-10-21). The protocol is now v1 with `warm` and `skipped` messages, the pool is the `WorkerPool` class of `src/client/pool.ts` (one pool per worker kind, 1 worker by default, timeouts and idle termination), and the UI lives in `demo/src/ui`. The current design is in [architecture.md](architecture.md); the demo still keeps 2 workers.

- **Protocol** (`src/worker/protocol.ts`): requests `analyze {id, file, engine, options}` and `cancel {id}`; responses `progress`, `result`, `error {message, aborted}`. `engine` is `own | mp4box | mediabunny`; rVFC never goes through the worker. Options exclude `signal` and `onProgress`; the worker creates an `AbortController` per job id and throttles progress to one message per 50 ms. The `File` travels by structured clone, with no byte copy.
- **Pool** (`workerPool.ts`): up to 2 module workers, spawned lazily, FIFO queue. Cancel removes a queued job, or posts `cancel` and rejects with `AbortError` at once; a worker that is still busy 1.5 s later is terminated and replaced. A worker crash rejects the job and respawns.
- **Store** (`store.ts`): an external store read with `useSyncExternalStore`. The Matroska mode (default `auto`) applies to files added later and re-runs finished Matroska rows. "Scan all frames" is a rescan in exact mode. A cancelled first analysis leaves `Cancelled`; a cancelled rescan keeps the previous result.
- **Compare panel** is a lazy chunk. Opening it auto-runs mp4box (MP4/MOV only) and mediabunny; rVFC runs only on an explicit click (`Run (approximate)`), in the panel's host element or in a temporary fixed visible div on `body`. Closing the panel during an rVFC run detaches its host and is not handled.
- **Download JSON and Copy JSON** export one envelope (`schema: video-fps-probe/export@1`, `app`, `environment`, `settings`, `results`; architecture.md, JSON export). `results` are the own results, plus a `compare` object keyed by engine for rows with finished comparison runs. Copy tries the async clipboard, then `execCommand('copy')` on a hidden text area, and when both fail shows the JSON in a read-only text area to select by hand (iOS on plain http, locked-down browsers). The write starts synchronously inside the click handler because Safari rejects a clipboard write after an `await`; Playwright's WebKit cannot prove that rule, so it needs a real iPhone. Both buttons stay disabled until a result exists.
- **Device line.** The footer shows, for example, "Chrome 155 on Windows 10, 16 threads, 1280x900 @1x" (`data-testid="env-line"`). Where Chromium exposes UA client hints it adds the real OS version and the Android model, because Chrome on Android otherwise reports a frozen "Android 10"; macOS versions are left out because browsers freeze them at 10.15.7. The module is a lazy chunk (2.24 KB gzip) loaded on idle after the first result, or by the first export, so it is outside the initial and first-analysis composites. It used to load right after the first render, which put it on every page load without being counted (fixed 2026-10-21).
- **Hooks for benchmarks.** `window.__fpsProbe` has `results` (finished rows in display order), `pending` and `runEngine(index, engine)`. DOM hooks: `input[data-testid="file-input"]` (multiple, focusable), `article.card`, `.summary` (`role=status`), `details.cmp`, `.rvfc-host`.
- **Samples.** `demo/public/samples/` holds 6 files (741,065 B) fetched into in-memory `File` objects, so their reads never touch the disk and timings are optimistic; the UI says so.
- **Layout.** Light and dark through CSS variables, a 2-column card grid at 480 px and below. The e2e 360 px test found a horizontal overflow with the Compare panel open: `section.list` is a grid with an `auto` track, so the card (min-width auto) took the table's min-content width (594 px in a 360 px viewport) and the `.scroll` wrapper never scrolled. The fix is `grid-template-columns: minmax(0, 1fr)` on `.list`.
- **Verified in headless Chrome 155** (own profile, driven over CDP): 100 fixtures dropped at once gave 100 results in drop order in 0.2-0.4 s wall with the pool of 2 and zero console errors; header mode shows "Scan all frames" on Matroska cards and the click upgrades them to `exact`; all 6 samples run through own, mp4box and mediabunny. The 360 px check of that pass missed the overflow above, which the e2e suite caught. The real rVFC engine was verified separately (section 5); a full visible-tab GPU run is not covered.
- **Bundle.** The first build, with both parsers inside the worker entry, measured main 73.67 KB gzip (limit 75), worker 23.93 KB (limit 12) and initial total 99.24 KB (limit 85); lazy mp4box 43.59 KB, mediabunny 52.46 KB, Compare 1.19 KB, shared counting 1.48 KB. The research prototypes were 5.5 KB (MP4) and 4.9 KB (EBML); the complete parsers are about twice that. Loading each parser as its own chunk on first use moves them out of the worker entry (architecture.md, Lazy chunks), and the budgets are now per chunk in `BUDGETS` of `scripts/size-report.mjs`. `npm run build && npm run size` gives the current numbers. The rVFC engine is 2,136 B gzip alone, of which about 270 B are core result builders that disappear when `core/result.ts` is shared with another chunk.

## 7. Compare rules and harness

- **Known deviations** are per engine files, `fixtures/known-deviations/<engine>*.json`, merged for `own` (`own-isobmff.json`, `own-matroska.json`); the format is in `fixtures/known-deviations/README.md`. They replace the single `fixtures/known-deviations.json` of research 6.3. An entry applies only to a would-be mismatch, and an unused one is reported as stale.
- **ISO BMFF `avgFps`** is two checks: the plain one compares `avgFpsFfprobe` (falling back to `avgFps`) with `avg_frame_rate` exactly, and `measured` compares `avgFps` with `avgFromPts` when the app built a presented timeline (provenance exact). `measured` is within-tol when the frame counts match and the spans differ by less than one median delta, which happens when ffprobe fills the last packet duration itself (VP9 in MP4: 133 ticks for every packet against stored 128 and 144).
- **Built-in sidx rule.** The `avgFps` check is `known-deviation` (source `[built-in]`) when the app differs from ffprobe, equals the reference `avgFromPts` within 1e-9 relative, and the file is fragmented with a sidx (found by an independent top-level scan, not by the app). Since the plain check reads `avgFpsFfprobe`, only the library engines reach it; the two own sidx entries were removed from `own-isobmff.json`.
- **Primary track** for MP4/MOV uses ffprobe `disposition.default` as the tkhd enabled flag; Matroska uses the first video stream.
- **Matroska `avgFps`** is two checks: `declared` (`avgFpsFfprobe` vs `avg_frame_rate`) and `measured` (only after an exact scan, vs `avgFromPts`, within 1e-9). `measured` is within-tol when the track stores no duration for its last frame (no DefaultDuration and no BlockDuration in the file scan) and the app's average equals the frames over the timestamp span plus one median delta exactly, so a last frame of any other length, zero included, still mismatches. Such a check is a definition difference by design, and its detail says so: `avgFps` gives the unstored last frame the median interval (the presented-frames definition), ffprobe its own estimate, and ffprobe parity is the `declared` check of `avgFpsFfprobe`. Whether the track has a DefaultDuration comes from an independent scan of its Tracks element (`scanMatroskaLayout` in `scripts/compare/layout.ts`, not from the app; the manifest note is the fallback when the scan fails), so a parser that silently loses DefaultDuration is still caught. Without one, `declared` and `nominalFps` compare the ffprobe estimate (section 3) with `avg_frame_rate` and `r_frame_rate` exactly, and a missing estimate is a mismatch once blocks were read; they are `n/a` only in header mode, which reads no block. A manifest note that says DefaultDuration is absent while every video track of the file has one stops the run as a harness error (exit 2).
- Matroska `frames`, `presentedFrames`, `startSec` and measured `avgFps` apply only after an exact scan; estimated or sampled counts are `n/a`.
- **Hybrid fragmented** files: `frames` is the total packet count when `nb_frames` is smaller. The moov-only count is not checked because `FileResult` has no field for it. When `nb_frames` is larger (truncated mdat), `frames` equals `nb_frames`.
- **Outcome rule** for `error`: `expect=ok` needs no error, at least one track and a primary; `no-video` needs zero tracks and no error other than "no video"; `still` needs only single-sample tracks; `error` needs an error and zero tracks.
- Per-track checks run for every video track, one table row each (`name (track N)`), primary first.
- **Library engines** are loaded by the single `analyze*` export of `src/engines/<name>.ts`; large fixtures run once for them, and `--with-large` adds every local file in `fixtures/large` that is present (the 3 h and 1 h long files, the 604 MB big files, the sparse files). mp4box and mediabunny are exact on the 3 h CFR file (648,000 frames); both report 3600.001 s against 3600.000 s format duration for the 1 h VFR file.
- Exit codes: 0 ok, 1 an unexpected own mismatch or throw, 2 harness error. `--filter` writes `report/accuracy.local.*`, which is git-ignored. `--self-test` runs 162 checks, including an oracle round trip that builds a synthetic app result from each of 116 ffprobe references and requires zero mismatches.
- **Size report.** `scripts/size-report.mjs [dist] [--check]` finds the worker through the `Worker()` reference or the manifest, classifies the chunks, checks the limits in its `BUDGETS` table and reports the remaining lazy chunks without a limit. It knows the rate profile chunks (`segments`, `rateProfile`, not required) and the device info chunk (`deviceInfo`, unbudgeted), and adds a first VFR MP4 composite (initial + ISO BMFF + segments, 97.84 KB against 100 KB). Its component limits add up to 100.5 KB, so that composite can trip while every chunk is within its own limit. `--self-test` runs 142 checks.
- **Header-mode caveat.** With `--mkv-mode header`, min, max and VFR are null by design; they must be rated `n/a` rather than compared (78 false mismatches otherwise).

## 11. Rate profile

Uneven frame distributions must be visible (half a video at 5 fps and half at 200 fps, freezes, bursts) without growing the bundle. The profile is `src/core/segments.ts`, a lazy chunk.

- **Trigger.** `analyzeTimeline` records the smallest and largest positive interval. Only when the largest is more than 7.5% above the smallest (`CUSUM_DRIFT`, half of `RATE_CHANGE_RELATIVE` = 15%) does it return a `ProfileJob`, a closure over the interval source: run-length stts runs for MP4 (no per-frame array on the fast path), the sorted PTS for Matroska. CFR tracks get no job. Matroska gets a profile only after an exact scan; probe and header results have none.
- **Deferred job.** After a track's result is built, the parser calls `rateProfileOf(job)`, which imports `segments.ts` once per worker. A failed import gives `rateProfile: null` instead of a failed file. The work stays inside `analyze`, so `io.ms` includes it.
- **Segmentation.** One pass over `(count, interval)` runs in timeline order. A two-sided CUSUM tracks the deviation of each interval from the running mean `m` of the current segment, with drift `k = 0.075 m` and alarm level `h = 2 m` (`CUSUM_ALARM_PERIODS`). Runs of equal intervals inside the drift are consumed in one step. On an alarm the segment is cut where the deviation started; the boundary frame goes to the side whose rate it fits better (log ratio).
- **Holds.** A single interval of at least `max(0.5 s, 4 m)` (`FREEZE_MIN_SEC`, `FREEZE_FACTOR`) closes the current segment and becomes a hold span.
- **Short spans.** A span needs 5 frames and 0.5 s (`MIN_SEGMENT_FRAMES`, `MIN_SEGMENT_SEC`) to be a segment. A shorter one joins the neighbouring steady segment with the closest rate and becomes an anomaly: `freeze` when its mean interval is at least `max(0.5 s, 4 x the neighbour's mean interval)`, `gap` when its rate is more than 15% lower, `burst` when more than 15% higher; otherwise it merges silently. A long span that never settles is a `variable` segment.
- **Merging and rate changes.** Adjacent steady segments within 15% of each other merge. A `rate-change` anomaly marks each remaining boundary between segments whose rates differ by 15% or more, and every boundary between two steady segments.
- **Uneven.** The steady segments are sorted by rate and a sliding 15% band finds the dominant band by time (freeze time excluded) and by frames. `uneven` is true when that band covers under 80% of the time (`UNEVEN_DOMINANT_SHARE`) or of the frames, or when steady segments differ by 15% or more. A regular cadence (2:3 pulldown, `select` drops) stays one steady segment, VFR but not uneven.
- **Buckets.** `min(120, frames / 2)` equal buckets over the PTS span; each interval spreads its frame over the buckets it covers. The UI draws them on a log scale.
- **Output.** At most 50 segments and 50 anomalies, with counts of the rest; `dominantShare`; a summary of the first three segments plus anomaly and duplicate counts, for example `Uneven: 5 fps for 4 s, 200 fps for 4 s`.
- **Tests.** `tests/unit/segments.test.ts` uses synthetic timelines; `tests/segments/fixtures.test.ts` asserts the profiles of the VFR fixtures, that none of the 21 `cfr_` fixtures gets a profile (also the 120 and 240 fps WebM files, whose 1 ms ticks spread more than 7.5%: the gate skips a track the VFR rule calls CFR when the spread is within the VFR tolerance and below 2x, section 4), that every VFR fixture gets one and no fixture the VFR rule calls CFR does, and that every profile tiles the presented frames. The e2e suite checks the uneven badge and the two-segment table in the browser.
- **Size and cost.** In the demo build the core chunk is 1.84 KB gzip (budget 2.00 KB) and the panel 0.94 KB (budget 1.50 KB); a first VFR MP4 loads 101.23 KB in total (budget 101.50 KB, `report/size.md`). In Node `vfr_two_phase_5_200.mp4` takes 0.48 ms in all and the 3 h CFR file is unaffected (3.54 ms). On the 1 h VFR screen recording (133,920 frames, 1439 gaps) the analysis takes 55.4 ms in Node and 70.4 ms in Chrome (`report/accuracy.md`, `report/browser-bench.md`), against 31.7 ms and 31.1 ms in the reports committed before the profile (README of commit 3e475b2). With the profile job switched off in a scratch copy of `src/core`, the same file takes 27 to 28 ms in Node against 45 to 48 ms with it (median of 9 runs each), so the profile is about 40% of the time on long VFR files.
- **Known gaps** (section 9): the stored duration of the last sample is not used, so a long final hold is missing and the end can overshoot by a few ms; a segment's duration includes its freezes while its rate excludes them.

### Added

- `video-fps-probe/react`: `VideoFpsProvider`, `useVideoFps(file, options)` with `{ status, result, summary, error, progress, cancel, retry }`, `useVideoFpsProbe()` and `usePrewarmVideoFps()`, for React 18 and 19 (an optional peer, `^18.0.0 || ^19.0.0`, so npm refuses the install next to a React major that was not tested, with `ERESOLVE`, unless the app passes `--legacy-peer-deps` or overrides the peer). The provider takes the probe and is required: there is no default probe, so the entry never reaches the own worker literal, and a hook outside a provider throws `ProbeError('engine-not-registered')` with `wrap in VideoFpsProvider`.
- `useVideoFps` keeps its state in a framework-free store, unit-tested in Node, which caches results per provider in a `WeakMap` by Blob, then by engine and options, runs one analysis through the double effects of `StrictMode`, starts nothing during a server render, aborts a pending analysis when its last component unmounts and starts it again when a component subscribes again (a memoized component that `<Activity>` hides and shows again included), and fetches `summarize` as a lazy chunk in parallel with the first analysis.
- In the React entry, only the `summarize` chunk failing to load gives `worker-failed` with `reason: 'load'`; a rejection that is not a `ProbeError`, an `analyze` of a custom probe that throws synchronously or a summary that throws gives `reason: 'crash'` (a thrown `ProbeError` is kept), and every failure settles to the error state instead of throwing from `subscribe`. `dist/react/index.js` starts with `'use client'`; `check-dist` requires that and fails on a `react` or `react-dom` import outside `dist/react/` ([React](api.md#react)). The cap of the unpacked package moves from 460 to 470 KB for the entry.
- `video-fps-probe/check`: `check(result, rules)` judges a result against upload limits in the calling thread, before the upload round trip. The rules are JSON: `fps` (`min`, `max`, `exact`, `oneOf`, and `source`: the presented average by default, or ffprobe's average, the nominal or the dominant rate; on a constant track with 1 ms timestamps the default judges the nominal rate, since the rounded span puts the average a little off it and a 60 fps WebM would otherwise break `max: 60`, and the duration of such a track is its frames over that rate), `duration` (compared at the microsecond, the 6 decimals ffprobe prints, so a 59.94 fps WebM whose ffprobe duration is 3.003000 meets `min: 3.003`), `frameSize`, the stored frame size after rotation without the sample aspect ratio (`minWidth` to `maxLongSide`; named `frameSize`, not `display`, because a pasp box or a Matroska DisplayWidth is not applied), `aspectRatio` and `pixels` of that size, `fileSize`, `containers`, `codecs`, `audio` (`'required'` or `'forbidden'`, unknown for an rvfc result, whose engine counts no audio tracks), and `vfr` and `uneven` policies (`'allow'`, `'warn'` or `'reject'`; a missing `isVfr` or a rate profile without `uneven` is unknown, not constant or even). The entry imports no module at run time, which `check-dist` enforces ([Check](api.md#check)).
- `check` bounds are inclusive and compared as exact rationals, so 23.976 fps (`24000/1001`) is below a minimum of 24 and 59.94 meets a maximum of 60. A frame rate bound written as the decimal 23.976, 29.97, 47.952, 59.94 or 119.88 holds for the decimal and for its x/1001 rate, so `max: 29.97` accepts `30000/1001` and `exact: 23.976` matches `24000/1001`. With the default source, on a constant track on 1 ms ticks a frame rate bound also holds within the resolution of the timestamps, so `exact: '60000/1001'` matches the `19001/317` that the DefaultDuration of a 59.94 fps WebM stores, and `exact: 60` does not. A violation message prints the actual rate or duration with enough decimals to differ from the bound it breaks.
- The `check` report has a verdict (`pass`, `warn`, `fail` or `unknown`), the violations with the rule, severity, expected and actual values and a message, and a `suggestedFps` with a plain reason when the rate or its evenness breaks a rule: a rate every bound of the `fps` rule allows, named exactly in the reason and preferring a standard rate between the bounds (23.976 to 120 fps, the x/1001 rates included; a plain 1 in k decimation first, else the nearest, so 60 fps under `max: 29.97` gets 29.97 (30000/1001) and not 20), or `value: null` with a reason when no rate meets every bound (an empty `oneOf`, a `min` above the `max`, an `exact` rate outside them). An empty `oneOf`, `codecs` or `containers` list fails every file, and its message says `is not one of an empty list`.
- For `check`, a missing result, a result with an error or without `videoTracks` (a partial or older JSON) and a missing field give `unknown`, never an exception, so an upload flow can fail open; such a result still fails a file size or a container it breaks. Malformed JSON gives `unknown` too, never an exception, with a message that says what is missing: a result that is not an object, null or non-object entries of `videoTracks`, tracks without a `trackId`, a `primaryTrackId` that is missing or matches no track, and fields of the wrong type; an `error` that is not a non-blank string is described, not printed. An unknown `fileSize` or `containers` names its own missing field, not the video track those rules do not need.
- `check` throws for a broken rule: a rule value of the wrong type or outside its list, such as `audio: 'require'`, a list where an object or a single bound is expected, a ratio string in `duration`, `frameSize`, `pixels` or `fileSize`, which take a finite number or a decimal string that is finite as a double (`'1:30'` is not 1/30 s, and `'1e400'` throws), and a key that is not a rule, such as `fps.mxa`, throw a `TypeError` naming the rule, so a typo cannot turn a limit off.
- `video-fps-probe/presets`: the published input limits of six video generation APIs for a reference or source video, as `check()` rules, each with `sourceUrl`, `sourceKind` (`'official'` or `'gateway'`), `verifiedAt` and a `note`: `klingO1ReferenceVideo`, `klingMotionControl` (Motion Control 3.0), `runwayAleph2`, `veoExtend` (Veo 3.1), `wan26ReferenceToVideoFal` and `seedance2ReferenceVideo` (from the fal and EvoLink gateways, which serve another company's model, so their violations are warnings).
- Every preset number was read again from its source on 2026-10-25; limits a page leaves ambiguous or does not publish are left out and named in the note, such as the 4k size of Veo, the input resolution of Aleph and the codecs of Kling. No page says whether its MB is decimal or binary, so a size limit holds the larger reading, MiB, and the note names it: a file reported over it is over under either reading.
- Each preset is a named export of a module with no imports, so a host bundles only the presets it imports, and it is typed read-only and frozen at every level, since every importer shares it: writing to a preset throws a `TypeError` in strict mode. The freezing call of each preset is annotated `/*#__PURE__*/`, so bundlers still drop the presets a host does not import. The preset tests require a source, a kind, a date and a note, and warn without failing when a preset was verified more than 90 days ago ([Presets](api.md#presets)).
- `ProbeError.reason` on every `worker-failed` the probe raises: `'load'` when code it needs did not load (the worker script, a chunk a worker loads for an engine or warms, a main-thread chunk, the probe client of a lazy stub, or `new Worker()` threw), `'crash'` when it failed after loading. The code stays `worker-failed`. The worker protocol's `error` reply gets an optional `reason: 'load'`; the version stays 1 ([Errors](api.md#errors)).
- `avgFpsFfprobe` and `rFpsFfprobe` for a Matroska or WebM track without DefaultDuration: the `avg_frame_rate` and `r_frame_rate` that ffprobe 8.1.1 estimates from the first packets, reproduced bit for bit in `matroskaMode` `probe`, `exact` and `auto` (`header` mode reads no block and leaves both null). It covers browser MediaRecorder recordings, which never store a DefaultDuration: the 12 committed files without one, 8 Chromium recordings among them, now give ffprobe's strings (60/1 or 60000/1001 on the recordings, `0/0` where ffprobe prints that), and 503 more Matroska files without one, generated from the recordings with random timing and late Opus audio, matched ffprobe on both strings. The code is a lazy chunk, `core/rfps.js` (3.60 KB gzip in the size matrix), which the Matroska parser loads only for such a track and which reads only the first packets: 41 video packets of a Chromium recording, 48 for H.264. Outside the reproduced cases (other codecs, more than one video track, tracks other than Opus, laced blocks, H.264 that is not Baseline, signals timing or reordering, or whose headers do not fix the decoder delay at 0 or that does not start with an IDR, AV1 with timing info, damaged first Clusters) both stay null and the warning names the reason ([implementation notes](#ffprobe-frame-rates-without-defaultduration-020)).

### Fixed

- `avgFpsFfprobe` and `rFpsFfprobe` of a Baseline H.264 track in Matroska without DefaultDuration could be an estimate that assumes no decoder delay where ffprobe's decoder raises its reorder delay to 1: without a VUI `bitstream_restriction`, FFmpeg does that when the picture order count of a decoded frame steps by more than 2 or goes back, and its strings then differ when the blocks carry durations. The parser now reads the PPS and the slice headers of the first 7 packets, the ones the decoder sees, and reports no estimate, with the reason in the warning, for a POC step other than 1 or 2, a `frame_num` gap, `pic_order_cnt_type` 1, field coding, a bottom field POC offset or a slice header it cannot read. With or without `bitstream_restriction`, it also reports none when the first packet is not an IDR: FFmpeg outputs no frame for a first I slice that is not one, so its dts start one packet later than the estimate assumes, and on 240 Baseline files built that way 5 of 166 estimates differed from ffprobe. With a `bitstream_restriction` that fixes the delay at 0 the parser used to skip the slice headers; FFmpeg then outputs no picture whose POC goes back below the last one it output (`h264_select_output_frame` with `has_b_frames` 0), which starts its dts a packet later too, so the parser now reads them there as well and reports no estimate for a POC that goes back, a `frame_num` gap, `pic_order_cnt_type` 1 or field coding; a step forward of any size keeps the estimate. That check adds 0.04 KB gzip to the `rfps` chunk. A Chromium recording, whose SPS has `bitstream_restriction` with no reordering, is unaffected, and so is every committed fixture. The SPS in CodecPrivate or in the first block is now read only up to its own length. The `rfps` chunk grows by 0.63 KB gzip for it, and so do all own paths, the one-file workers, which inline the chunk, and the emitted lazy totals, which carry it twice, in the worker and in the main-thread copy. The critical path and the first MP4 of the default configuration did not change. The cap of the unpacked package moved from 450 to 460 KB ([implementation notes](#ffprobe-frame-rates-without-defaultduration-020)).
- The mp4box engine (`video-fps-probe/mp4box`, the tuned adapter) ended a fragmented track at the sum of its trun sample durations. It now follows the tfdt timeline, as ffprobe and the own parser do: a fragment with a tfdt starts there, and the track ends at the latest fragment end. Chrome MediaRecorder fMP4, whose fragments end with a placeholder sample duration of 999 ticks, now gets ffprobe's track and format duration (4.524533 s instead of 4.557667 s on `rec_chromium_h264.mp4`).
- A worker script that failed to load, for example a 404 in a tab opened before a redeploy, was reported as a crash: a bare `worker failed`, or `Uncaught SyntaxError: Unexpected token '<'` when Chromium parsed the 404 page as a classic worker. Any worker `error` event before the worker's first reply now rejects with `reason: 'load'`, the message `worker script failed to load or parse; the app may have been redeployed`, followed by the event's message when it has one, and the error event as `cause`. An `error` event after the first reply stays `reason: 'crash'`. While another worker of the pool is alive, the job waits for it and no further worker starts until the next call; when the failed worker was the last one, its job and the queued jobs reject once instead of fetching the script again for every queued file. The next call loads the worker again.
- A failed `warm` replied without `reason`, so a prewarm whose engine or parser chunk did not load was tagged `crash`. It now carries `reason: 'load'`.

### Changed

- Behaviour change: a lazy stub whose probe client chunk fails to load rejects with `ProbeError('worker-failed')`, `reason: 'load'` and the import error as `cause`, instead of the browser's import error as it was, so every rejection of a probe or a stub is a `ProbeError`; a `ProbeError` of the factory is passed through. ### Known limitations

- Zero-config Vite (iife workers) loads 38.92 KB for the first MP4: the probe client and one 36.02 KB worker file with both parsers. `worker: { format: 'es' }` brings it to 23.59 KB.
- Only Vite 8 is verified; the other bundlers are documented, not tested ([bundlers](bundlers.md)).
- The browser floors (Chrome and Edge 94, Firefox 114, Safari and iOS 15.4; mp4box.js needs Safari 16.4) are derived from the features used, not tested on those versions; CI runs the Chromium, Firefox and WebKit builds of Playwright 1.64.1. In-thread `analyze()` is tested on Node 24 only.
- The corpus has real recordings from Chromium's MediaRecorder only: no Firefox or Safari recordings, and no phone, camera or screen recorder files.
- `avgFpsFfprobe` and `rFpsFfprobe` of a Matroska track without DefaultDuration are reproduced only in the cases listed above; elsewhere they are null and a warning names the reason.
- A regular cadence such as 2:3 pulldown is VFR, but its rate profile reads as Steady.
- `check` judges the stored frame size: the sample aspect ratio of a `pasp` box or a Matroska DisplayWidth is not applied.
- `check` judges the `duration` of a VFR WebM or Matroska track on 1 ms ticks by its measured span, which can be up to about one frame interval shorter than the container duration ffprobe prints: `vfr_screenrec_ts1000.webm` lasts 5.999 s against ffprobe's 6.000000, so `duration: { min: 6 }` fails it.
- rVFC needs playback: a visible foreground tab, a playable codec and seconds per file.
- Files above 2^53 bytes, `cmov` headers and a moov above 256 MiB are rejected as error results.
- In `auto` mode a large Matroska file gets a sampled probe unless the exact scan is predicted to take at most 150 ms, plus the first packets that probe mode reads for the ffprobe estimate of a track without DefaultDuration.

## 15. 0.3.0 design notes

### One own worker per container family

The default flavor runs own on two workers, one per container family, and the client picks the worker from the first 4 bytes of the file. 4 bytes are enough because they decide exactly the first branch of `sniff()` in `src/core/sniff.ts`: an empty head is unknown, a head that starts with the EBML magic `1A 45 DF A3` is Matroska, and nothing else ever is. Every other head, an ISO BMFF box, an unknown or foreign signature, a file of 1 to 3 bytes, goes to the ISO BMFF worker, whose own sniff then reads 1024 bytes and either analyzes the file or returns the same `not a recognised container` error as the combined worker of 0.2.0. So the route never disagrees with the worker's sniff, and `tests/unit/route.test.ts` checks it on the head of every fixture file, on short and foreign heads and on 10,000 random heads. A read that fails, an aborted read and a value that is not a `Blob` also go to the ISO BMFF worker, so `familyOf` never rejects and the worker still answers a non-Blob with its `protocol` error.

Each worker imports its parser statically and reaches neither the other parser nor the loaders of `core/analyze.ts` (`analyzeWith` in `core/dispatch.ts` holds the shared body). `check-dist` checks that on `dist/`, the size matrix on the sourcemaps of every consumer build. Two separate worker builds each hold a copy of the reader, the runtime and the statistics, so a session that analyzes both families loads about 8 KB more than 0.2.0 in the default configuration; a host that wants one worker can keep the 0.2.0 layout with a custom worker that serves `ownEngine`.

### Planned for 0.4.0

The 0.4.0 plan, the 0.4.1 bundler matrix and 0.5.0 are in the [README roadmap](../README.md#roadmap). One 0.4.0 item in detail:

- Expose a median frame interval and use it in `check()`. 0.3.0 judges the format duration of a WebM or Matroska track when it is within one frame interval of the measured span, the interval of `dominantFps`, else of `nominalFps` on a constant track, else of `avgFps` (section 3, track and format durations), so the Chromium recordings, which have no dominant rate, take their average interval of 27 ms rather than their median of 17 ms.

### Color: the container against the SPS VUI

H.264 and HEVC behave the same in the mov demuxer of FFmpeg 8.1.1: the container values are kept, and the decoder fills only what the container leaves unspecified.

- **Conflict.** `colr_vui_conflict.mp4` (H.264, colr BT.2020, PQ, BT.2020 non-constant, limited range over a VUI of BT.709, sRGB, BT.709, full range) prints every colr value. `colr_vui_conflict_hevc.mp4` (HEVC, colr BT.709 over a PQ VUI) prints the colr values too. `pix_fmt` still follows the VUI full range flag (`yuvj420p` on the H.264 file).
- **Only the colr speaks.** `colr_only_h264.mp4` (no VUI video signal type) and `colr_only_hevc.mp4` (a video signal type without a colour description) print the colr values.
- **Only the VUI speaks.** `hlg_h264_vui_only.mp4` and `hlg_vui_only.mp4` print the VUI values.
- **Unspecified codes.** The mov demuxer first turns every colr code that has no name in the FFmpeg primaries, transfer or matrix table into 2 (unspecified). The reserved codes 0 and 3 have the name `reserved` and count as specified (matrix 0 is `gbr`). Primaries, transfer and matrix then act as one group. When the colr gives at least one of the three as a specified code, ffprobe prints all three from the colr, an unspecified one as `unknown` (`colr_partial_h264.mp4`: bt709, unknown, unknown over a BT.2020 HLG VUI). When all three are unspecified, it prints the three VUI values (`colr_unspecified_hevc.mp4`). Scratch: a colr of 2, 16, 2 over a PQ VUI prints unknown, smpte2084, unknown. A colr of 200, 2, 2 on `hlg_h264_8bit.mp4` and of 2, 2, 200 on `hlg_hevc10.mp4` print the VUI values bt2020, arib-std-b67 and bt2020nc, because 200 has no name. A colr of 3, 2, 2 or 0, 2, 2 on `hlg_h264_8bit.mp4` prints primaries `reserved` and unknown for the other two.
- **Range.** The nclx full range flag always wins, also when its three codes are 2 (`colr_unspecified_hevc.mp4`: pc over a limited range VUI, `colr_vui_conflict.mp4`: tv over a full range VUI). nclc has no range field, so the range comes from the VUI (`colr_nclc.mov`: pc).

So the color rule of the 0.4.0 color reader has one row per member, the same for both codecs. A code is unspecified when it is 2 or has no FFmpeg name, and the reserved codes 0 and 3 are specified:

| Member | H.264 and HEVC |
|---|---|
| range | the nclx full range flag when the entry has an nclx colr, else `video_full_range_flag` when `video_signal_type_present_flag` is set, else none |
| primaries, transfer, space | the colr codes (nclx or nclc) when at least one of the three is specified, each unspecified code giving none, else the SPS values when `colour_description_present_flag` is set, else none |

So the container wins over the SPS, not the reverse. A container reader is right whenever a colr declares a value, and the SPS readers decide only the files whose container is silent: `hlg_h264_vui_only.mp4`, `hlg_vui_only.mp4`, `colr_unspecified_hevc.mp4`, and the range of `colr_nclc.mov`, `hevc_hvc1.mp4` and `hevc_hev1.mp4`. The two HEVC files have no colr, and their range tv comes only from the VUI video signal type.

- **Matroska.** The Colour element wins over the SPS like a colr, and the same rule applies to the CodecPrivate SPS (scratch, no committed file shows either case). `hdr10_hevc10.mkv` with its SPS rewritten to BT.709 by the `hevc_metadata` bitstream filter, the Colour still PQ, prints the Colour values bt2020, smpte2084 and bt2020nc. An x264 file in Matroska with HLG only in the VUI (`-x264-params colorprim=bt2020:transfer=arib-std-b67:colormatrix=bt2020nc`), whose Colour carries only the Range, prints the VUI values bt2020, arib-std-b67 and bt2020nc.

- **VP9.** `vp9_p2_10bit.webm` and `vp9_p2_10bit.mp4` print the PQ names. The Colour element, the vpcC, the colr and the frame header agree. The WebM file has no CodecPrivate, so its profile and bit depth are only in the bitstream.
- **AV1.** `av1_10bit.mp4` has no color box. ffprobe prints range tv from the sequence header and unknown for the other three.

### Names

- **HDR.** `color_transfer` is `smpte2084` for PQ and `arib-std-b67` for HLG. Primaries print `bt2020`, the matrix `bt2020nc`, the range `tv` or `pc`. `hlg_h264_8bit.mp4` shows that an 8-bit H.264 file keeps the HLG tags.
- **Profiles.** H.264 prints `Constrained Baseline` (profile_idc 66 with constraint_set1), `Main` (77) and `High` (100), HEVC `Main` (1) and `Main 10` (2), AV1 `Main` (seq_profile 0), VP9 `Profile 0` and `Profile 2`. The corpus also prints `Proxy` for ProRes, `Baseline` for MJPEG, `0` for VP8 and `unknown` for PNG, which carry no profile in a codec configuration. `scripts/compare/profiles.ts` holds the name table, and `compare-ffprobe --self-test` checks it against the codec configuration of every committed stream.
- **Bit depth.** HEVC, VP9 and AV1 at 10 bits print `pix_fmt` `yuv420p10le` and `bits_per_raw_sample` N/A, so the depth comes from `pix_fmt`.
- **Disposition.** In MP4 and MOV `disposition.default` follows the tkhd enabled flag. It is 0 on `track_disabled.mp4` (tkhd flags 2) and on the second video track of `multi_video_2tracks.mp4`, an older fixture whose second track has its enabled bit clear too, and 1 on every other MP4 and MOV video track. ### Sample aspect ratio

- **Precedence.** pasp, then the tkhd matrix, then the tkhd size, then the SPS VUI: `sar_pasp_tkhd_matrix.mp4` prints the pasp 4:3, `sar_tkhd_matrix.mp4` the matrix 2:1 over the tkhd size 3:2, `sar_tkhd_only.mp4` the tkhd size 3:2, `sar_vui_only.mp4` the VUI 4:3. So the matrix comes before the tkhd size. A pasp of 1:1 also wins over a VUI of 4:3 (scratch), and `sar_pasp_only.mp4` shows a pasp of 4:3 winning over a VUI of 1:1.
- **tkhd size.** The ratio is (stored height x tkhd width) : (stored width x tkhd height) with the integer parts of the 16.16 values. ffmpeg writes a tkhd width of 213.33 for the 4:3 ratio of a 160x120 stream, so `sar_tkhd_fraction.mp4`, such a stream without its pasp, prints 213:160. On the 1440x1080 stream of `sar_h264_4x3.mp4` the same ratio gives a tkhd width of exactly 1920, the display size 1920x1080, so that file carries no fraction.
- **tkhd matrix.** The column scales hypot(a, c) and hypot(b, d) give the ratio of the x to the y scale when both are above 1 in 16.16 units and they differ by more than 1 percent. Scratch: an x scale of 1.005 prints 1:1, and so do a uniform 2 times scale and a 90 degree rotation. FFmpeg multiplies the mvhd matrix into the tkhd matrix before it takes the scales, and applies them only when the tkhd width and height are not 0. Every ffmpeg-written file has an identity mvhd matrix, so no committed file shows the product.
- **Several sample entries.** With two avc1 entries in one stsd and every sample on the first, ffprobe prints the pasp of the last entry that has one: 4:3 then 16:11 prints 16:11, 16:11 then 4:3 prints 4:3, 4:3 then an entry without pasp prints 4:3, and an entry without pasp then 16:11 prints 16:11 (scratch, built from `sar_pasp_only.mp4`). A parser that reads the pasp of the first entry only differs on such a file.
- **MP4 without pasp.** With the tkhd size equal to the stored size and an identity matrix, ffprobe prints the VUI ratio (`sar_vui_only.mp4`), and with no VUI aspect ratio N/A for both ratios (`sar_none.mp4`). ffmpeg writes a pasp for every MP4 whose ratio is known, 1:1 included.
- **Matroska.** For a 4:3 ratio on 160x120, ffmpeg writes DisplayWidth 16, DisplayHeight 9 and DisplayUnit 3, and ffprobe prints 4:3 (`sar_4x3.mkv`), so the (PixelHeight x DisplayWidth) : (PixelWidth x DisplayHeight) rule holds for unit 3 too. FFmpeg applies Display elements only with a DisplayUnit below 4 and only when both are above 0. With unit 0 a missing element takes the pixel size, so a Matroska file without Display elements gets the ratio 1:1 from the container: scratch, an x264 file in Matroska with a VUI ratio of 4:3 (`-x264-params sar=4/3`) and no Display elements prints 1:1 and 4:3 for the display. With units 1 to 3 a missing element gives no container ratio.

### Fragmented output and the mfra

- Every fragmented file ffmpeg writes with `frag_keyframe` or `-frag_duration` ends with an mfra: with `empty_moov`, with `global_sidx`, with `dash`, with `cmaf`, and with an audio track (`fmp4_audio_longer.mp4`, `fmp4_audio_longer_sidx.mp4`). The `-f dash` outputs (`fmp4_dash_single_file.mp4`, `fmp4_dash_concat_segments.mp4`) have none, and neither do the sliced Chromium recordings.
- `global_sidx` with an audio track writes one sidx per track after the moov.
- `fmp4_audio_longer.mp4`: the format duration is 2.523220, the end of the audio. The video stream lasts 2.023242 s for 60 frames at 30 fps, because the first frame lasts 869 ticks of 1/15360 s where the others last 512, so the video is VFR.

### Other files

- `fmp4_mehd_valid.mp4` prints the format duration 4.004000, as without the mehd: ffprobe never reads it.
- `faststart_large_moov.mp4` has a moov of 72,831 bytes at offset 32, above a 64 KiB head read, with one stts entry per frame.
- `mov_cmov.mov`: ffprobe reads the zlib-compressed moov (30 frames, 1.001000 s). The own parser answers `unsupported: compressed movie header (cmov)`, so the manifest row expects an error with the code `unsupported`. The `expect` column states the outcome of the app, so the `error` check of this row is exact and not a known deviation, although ffprobe reads the file, as for `corrupt_png_named.mp4`.
