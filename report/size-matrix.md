# Package size matrix

What the package adds to a Vite 8.3.5 app in each configuration, measured by `scripts/size-matrix.mjs` on production builds of the consumer fixtures in `tests/consumers/fixtures/`. Each fixture installs the packed tarball (video-fps-probe-0.3.0.tgz) with mp4box 2.4.1 and mediabunny 1.62.1 into a directory outside the repository, so nothing resolves to the source tree. Every package Vite and the peers pull in is pinned to its package-lock.json version, rolldown 1.2.14 among them, so Windows and Linux emit byte-identical files. KB means 1000 bytes; every size is gzip level 9 per file, and totals are sums of files.

The critical path is the package code inside the host entry chunk, cut out of the entry chunk by its hidden sourcemap: what a host pays before any file is picked. Vite adds its preload helper to the entry chunk of any app with a dynamic import; it is listed and budgeted separately because a host that already code-splits has it anyway. Everything else loads lazily, on the first file or the first engine run.

First MP4: the probe client and the worker that serves own for an ISO BMFF file. The default flavor runs own on one worker per container family, picked by the first four bytes of the file, and the ISO BMFF worker holds its parser and the statistics. A custom worker that serves own (custom) loads the statistics chunk and the ISO BMFF parser chunk after its entry, the statistics in parallel with the parser. First MKV is the same for a Matroska or WebM file without DefaultDuration, the worst case, which also loads the ffprobe frame rate estimate. All own paths is every own path of both families with the rate profile core; in the default flavor it counts both workers, each with its own copy of the runtime and the statistics. A worker built as iife cannot split, so in zero-config and iife-nosplit each own worker is one file, and in standalone-url the standalone file holds both parsers. The routing by container family is in the probe client of the default flavor; a custom worker client imports it as a chunk of its own only with byContainer (standalone-split-url), whose client columns count it, and never fetches it without (custom, standalone-url). createProbeClient (custom-eager) puts the probe client in the entry chunk, so its critical path counts the client and its lazy columns do not; it imports the routing chunk on the first own analysis with byContainer, and its entry chunk holds none of it.

The host's worker option decides the first MP4: 23.07 KB with `worker: { format: 'es' }` (default), 24.86 KB with no worker option (zero-config), because Vite's default worker format is 'iife'. In Vite 8.3.5 zero-config and iife-nosplit build byte-identical own worker files: with format 'iife' Vite already inlines the worker's dynamic imports, so `codeSplitting: false` changes nothing.

In react (React 19.3.1) and react18 (React 18.3.1) the entry chunk also holds React and ReactDOM, which a React host ships anyway, so its column is not a package cost. The critical path counts the package code only, and the React entry is 1.20 KB of it in each. The first analysis also fetches the 0.43 KB summary module of the store, in parallel with the probe client.

In check, 3.99 KB of the 4.55 KB critical path is `check`, imported statically next to the lazy stub. It imports no other module and loads nothing lazily, so the lazy columns equal the default configuration's.

In preset, 3.99 KB of the 4.90 KB critical path is `check` and 0.46 KB the one preset it imports (klingO1ReferenceVideo), imported statically next to the lazy stub. Neither entry imports another module or loads anything lazily, so the lazy columns equal the default configuration's.
