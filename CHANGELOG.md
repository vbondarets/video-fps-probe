# Changelog

Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versions follow semver with the [0.x policy](docs/api.md#versioning).

## Unreleased

These changes go into 0.2.0, a minor release under the [0.x policy](docs/api.md#versioning): `ProbeError.reason` is a new optional field, and a lazy stub whose probe client fails to load rejects with a `ProbeError` instead of the browser's import error, which code that tested that error has to follow (see Fixed).

### Added

- `video-fps-probe/react`: `VideoFpsProvider`, `useVideoFps(file, options)` with `{ status, result, summary, error, progress, cancel, retry }`, `useVideoFpsProbe()` and `usePrewarmVideoFps()`, for React 18 and 19 (an optional peer, `>=18`). The provider takes the probe and is required: there is no default probe, so the entry never reaches the own worker literal, and a hook outside a provider throws `ProbeError('engine-not-registered')` with `wrap in VideoFpsProvider`. The state comes from a framework-free store, unit-tested in Node, which caches results per provider in a `WeakMap` by Blob, then by engine and options, runs one analysis through the double effects of `StrictMode`, starts nothing during a server render, aborts a pending analysis when its last component unmounts, and fetches `summarize` as a lazy chunk in parallel with the first analysis. `dist/react/index.js` starts with `'use client'`; `check-dist` requires that and fails on a `react` or `react-dom` import outside `dist/react/` ([React](docs/api.md#react)). The unpacked package passes 460 KB with the entry, so its cap moves from 460 to 470 KB.

- `ProbeError.reason` on every `worker-failed` the probe raises: `'load'` when code it needs did not load (the worker script, a chunk a worker loads for an engine or warms, a main-thread chunk, the probe client of a lazy stub, or `new Worker()` threw), `'crash'` when it failed after loading. The code stays `worker-failed`. The worker protocol's `error` reply gets an optional `reason: 'load'`; the version stays 1 ([Errors](docs/api.md#errors)).
- [Deploy skew](docs/bundlers.md#deploy-skew): what a tab opened before a redeploy sees and how to recover.
- Three late-change fixtures (Tier L, 443 KB together): `late_30_to_60.mp4`, `late_25_to_12.5.webm` and `late_freeze_10s.mkv`, constant for more than 5000 frames before the rate changes or the picture freezes. The own parsers have no mismatch (every scored check exact); mediabunny's default recipe, which probes 256 packets, reports the first rate and no VFR, and its full scan is correct but several times slower. The predictions were committed before the first run; the own prediction failed on that run with one mismatch caused by a wrong manifest note, and the results, that correction included, are in [the benchmarks](docs/benchmarks.md#late-rate-changes-tier-l).
- Twelve browser recordings (Tier R, 869 KiB together): real MediaRecorder output of headless Chromium 156, WebM VP8, VP9 and AV1, Matroska H.264, and fragmented MP4 with H.264 and VP9, each in one piece and with a 250 ms timeslice, recorded by the new `scripts/fixtures/record-mediarecorder.mjs` and committed as recorded (CC0, [provenance](fixtures/README.md#browser-recordings-tier-r)). The own parsers have no mismatch on them, and the rate profile recovers the recorded pacing. The eight WebM and Matroska files store no last frame duration: ffprobe estimates it from its rate, the own parsers take the median interval. Their measured averages therefore differ from ffprobe's packet average by definition, by design and not by a measurement error: `avgFps` is the presented frames over the presentation span, and ffprobe parity is `avgFpsFfprobe`. `npm run compare` scores that difference within tolerance and labels it a definition difference by design, only when the average is exactly the frames over the timestamp span plus one median interval, so a last frame of any other length, zero included, is still a mismatch. The same rule covers `vfr_concat_10_30_60.webm`, a per-file known deviation before; those 9 checks are 9 of the 13 own within-tolerance verdicts, and the own deviation files are empty. WebKit on Windows has no MediaRecorder, and Firefox recordings wait for the manual `record-firefox` workflow.
- `npm run compare` runs the libraries in five arms: `mp4box-idiomatic` (the mp4box.js README recipe and its own fields), `mediabunny-idiomatic` (the mediabunny README metadata recipe, `input.computeDuration()` included, and `computeFrameRateMetrics()` with its defaults), `mediabunny-full` (`targetPacketCount: Infinity`, with its `probedPacketCount` as the frame count), and `mp4box-tuned` and `mediabunny-tuned`, this package's adapters, which were the `mp4box` and `mediabunny` engines (both names still select them). Each mismatch of an arm is classified as wrong, definition differs (the definition the library documents or implements for the field, evaluated on the file; each arm is checked against its own definitions only, mediabunny's `computeFrameRateMetrics()` replayed on the reference timestamps, `getDurationFromMetadata()` on the media headers, and its end timestamps with the zero duration it gives a Matroska last frame whose duration the file does not store), unverified (that definition cannot be evaluated on the file, or the value only equals a quantity the arm does not use, so it is counted neither as wrong nor as a definition difference), not provided or unsupported container, and [the accuracy section](docs/benchmarks.md#accuracy-vs-ffprobe) lists where the libraries win: every check where an arm is exact or within tolerance and the own parsers are not, over all fixtures with the large local files (marked when the arm's VFR flag on that track is wrong, or when the own parsers report the same value under a not applicable verdict), and the files an arm reads with fewer bytes or reads or in less time, counted on the files that both it and the own parsers open.
- Demo: when a file fails because code did not load, the page checks whether another build is deployed. If so, it shows one banner, "A new version of this page was deployed. Reload to continue.", with a Reload button, and the files read "Not analyzed."; if not, each file reads `Worker could not be loaded:` with the error.
- `avgFpsFfprobe` and `rFpsFfprobe` for a Matroska or WebM track without DefaultDuration: the `avg_frame_rate` and `r_frame_rate` that ffprobe 8.1.1 estimates from the first packets, reproduced bit for bit in `matroskaMode` `probe`, `exact` and `auto` (`header` mode reads no block and leaves both null). It covers browser MediaRecorder recordings, which never store a DefaultDuration: the 12 committed files without one, 8 Chromium recordings among them, now give ffprobe's strings (60/1 or 60000/1001 on the recordings, `0/0` where ffprobe prints that), and 503 more Matroska files without one, generated from the recordings with random timing and late Opus audio, matched ffprobe on both strings. The code is a lazy chunk, `core/rfps.js` (2.76 KB gzip), which the Matroska parser loads only for such a track and which reads only the first packets: 41 video packets of a Chromium recording, 48 for H.264. Outside the reproduced cases (other codecs, more than one video track, tracks other than Opus, laced blocks, H.264 that is not Baseline, signals timing or reordering, or whose headers do not fix the decoder delay at 0, AV1 with timing info, damaged first Clusters) both stay null and the warning names the reason ([implementation notes](docs/implementation-notes.md#ffprobe-frame-rates-without-defaultduration-020)).

### Fixed

- `npm run compare` scored `avgFps.declared` of a Matroska track without DefaultDuration exact when ffprobe printed `0/0` and the engine reported no estimate after reading blocks, as if both had said the same. A missing estimate after a block read is a mismatch there too, its detail names ffprobe's `0/0`, and header mode stays not applicable with its reason. The own engine prints `0/0` itself, so its results do not change; mediabunny's idiomatic arm and its full scan get 2 more not-provided checks each (`vfr_concat_10_30_60.webm`, `vfr_two_phase_5_200.webm`). The self-test oracle now reports ffprobe's `0/0` the way the own estimate does.

- `avgFpsFfprobe` and `rFpsFfprobe` of a Baseline H.264 track in Matroska without DefaultDuration could be an estimate that assumes no decoder delay where ffprobe's decoder raises its reorder delay to 1: without a VUI `bitstream_restriction`, FFmpeg does that when the picture order count of a decoded frame steps by more than 2 or goes back, and its strings then differ when the blocks carry durations. The parser now reads the PPS and the slice headers of the first 7 packets, the ones the decoder sees, and reports no estimate, with the reason in the warning, for a POC step other than 1 or 2, a `frame_num` gap, `pic_order_cnt_type` 1, field coding, a bottom field POC offset or a slice header it cannot read. A Chromium recording, whose SPS has `bitstream_restriction` with no reordering, is unaffected, and so is every committed fixture. The SPS in CodecPrivate or in the first block is now read only up to its own length. The `rfps` chunk grows by 0.64 KB gzip (2.76 to 3.40 KB in the size matrix, 3.38 KB in the demo, budget 3.5 KB in both). That raises all own paths to 40.34 KB (budget 40.5 KB, was 40 KB) and, because a one-file worker inlines the chunk, the zero-config first MP4 to 38.55 KB (budget 39 KB, was 38.5 KB) and the standalone worker to 35.58 KB (budget 36 KB, was 35.5 KB); the emitted lazy totals carry the code twice, in the worker and in the main-thread copy, and their budgets moved by 0.5 to 1 KB. The critical path and the first MP4 of the default configuration did not change. The unpacked package reached 450.1 KB, so its cap moves from 450 to 460 KB ([implementation notes](docs/implementation-notes.md#ffprobe-frame-rates-without-defaultduration-020)).

- The mp4box engine (`video-fps-probe/mp4box`, the tuned adapter) ended a fragmented track at the sum of its trun sample durations. It now follows the tfdt timeline, as ffprobe and the own parser do: a fragment with a tfdt starts there, and the track ends at the latest fragment end. Chrome MediaRecorder fMP4, whose fragments end with a placeholder sample duration of 999 ticks, now gets ffprobe's track and format duration (4.524533 s instead of 4.557667 s on `rec_chromium_h264.mp4`).
- A worker script that failed to load, for example a 404 in a tab opened before a redeploy, was reported as a crash: a bare `worker failed`, or `Uncaught SyntaxError: Unexpected token '<'` when Chromium parsed the 404 page as a classic worker. Any worker `error` event before the worker's first reply now rejects with `reason: 'load'`, the message `worker script failed to load or parse; the app may have been redeployed`, followed by the event's message when it has one, and the error event as `cause`. An `error` event after the first reply stays `reason: 'crash'`. While another worker of the pool is alive, the job waits for it and no further worker starts until the next call; when the failed worker was the last one, its job and the queued jobs reject once instead of fetching the script again for every queued file. The next call loads the worker again.
- A lazy stub whose probe client chunk failed to load rejected with the browser's import error as it was. It now rejects with `ProbeError('worker-failed')`, `reason: 'load'` and that error as `cause`, so every rejection of a probe or a stub is a `ProbeError`; a `ProbeError` of the factory is passed through. Code that read a stub rejection without `instanceof ProbeError` as a load failure should read `e.reason === 'load'`.
- A failed `warm` replied without `reason`, so a prewarm whose engine or parser chunk did not load was tagged `crash`. It now carries `reason: 'load'`.
- Release: the version step carried the intro of the Unreleased section ("These changes go into ...") into the released section. It now drops the text before the first `###` heading and prints it. `preversion` stopped with a bare git error when `user.name` or `user.email` was missing, and went on when one was set to an empty value; it now fails in both cases, before the gates, and names both values ([Releasing](docs/releasing.md)).
- `npm run compare` took the absence of a Matroska DefaultDuration, which makes the declared average not applicable, from a regex over the fixture's manifest note, so editing a note could turn a gating mismatch into n/a. It now scans the Tracks element of the file, and a note that says the element is absent while the file has it stops the run with exit code 2.
- `npm run compare` classified the mediabunny tuned adapter's average of `rec_chromium_vp9.mp4` and `rec_chromium_vp9_sliced.mp4` as wrong, although it is the arm's definition, `computePacketStats().averagePacketRate`: the packets over the span from the first timestamp to the largest timestamp plus duration. The span ends at the stored duration of the last sample, a 999-tick placeholder where ffprobe gives that packet 500 ticks. The layout scan now reads that stored duration from the file (the last trun entry, or the last stts delta), and the two checks count as definition differs.
- The Tier L section of `docs/benchmarks.md` corrected its claim that mediabunny's 256-packet probe and its full scan give the same rates on every older fixture with one example only. `readme-tables` now lists every fixture where they differ on the primary track, from `accuracy.json` (the `probe-full` block): the three `vfr_two_phase_5_200` files, `elst_trim_vfr_copy.mp4`, `h264_vfr_remux.mkv`, `remux_cfr_120_ts16000.mp4`, `cfr_240_ts600.mp4` and the local `long_vfr_1h_screenrec.mp4`.
- The README said the fixtures were synthetic files made with ffmpeg, which stopped being true with the 12 Chromium recordings. The sentence is generated now and gives both counts (114 made with ffmpeg and 12 recordings of the 126 committed fixtures).
- CI: the check that every Playwright container image matches `@playwright/test` read `ci.yml` only, so `record-firefox.yml` could keep an old image after a version bump. It now reads every workflow file, names the file of each mismatch, and fails when it finds no image at all.
- `scripts/fixtures/record-mediarecorder.mjs` wrote into `fixtures/files` by default and overwrote a committed recording of the same name without a word. The output directory is now required, an existing file is refused (the run exits 1) unless `--force` is given, and `--list` needs no directory ([provenance](fixtures/README.md#browser-recordings-tier-r)).
- `docs/benchmarks.md` quoted hand-written totals under its headline that had gone stale: the committed-corpus line read 4 within tolerance and 9 known deviations where the report has 13 and 0. `readme-tables` now writes that paragraph, the fixture and check counts, the large local files and the browser bench scope included, as the end of the `headline` block.
- `report/README.md` quoted hand-written accuracy totals that had gone stale (1832 checks where the report has 2087). `readme-tables` now writes that paragraph from `accuracy.json`, and `--check` and the version step cover the file.
- Demo: the build time and commit moved from the bundle into meta tags of `index.html`, so a deploy without code changes no longer renames every lazy chunk and breaks the first file in tabs opened before it. CI builds the demo twice with different stamps and fails when a file other than `index.html` differs (`npm run check:stable-chunks`).
- Demo: a rate profile or compare panel chunk that failed to load took the whole page down. The panel now reads "Panel failed to load." with a Retry button that imports the chunk again, so a transient network error does not leave the panels empty for the rest of the session, and the page runs its deploy check, also for a parser chunk that a worker started before the deploy cannot import.
- Demo: an error text above 100 characters was cut into a collapsed note, which hid the URL of a chunk that failed to load. The cut is at 200 characters now.

### Changed

- In `exact` mode, and in `auto` when it picks exact, the ffprobe frame rate estimate of a Matroska track without DefaultDuration takes its blocks from the block walk of the exact scan instead of walking the first Clusters itself before it, and copies the packet heads it needs from the scanner's buffer. The first Clusters are read once, so the exact plan of `auto` now covers the estimate: a 20 MB 720p60 VP8 WebM without DefaultDuration takes 20 reads instead of 26 for the same 19.9 MB (median 30.5 to 29.3 ms over three interleaved runs in Node 24 from a local SSD), with the same strings, frames and warnings. `probe` mode keeps a walk of its own, because the probe reads only 32 blocks of the first Cluster. The estimate and the Matroska parser grow by 0.23 KB gzip: `rfps` 3.54 KB in the size matrix and 3.52 KB in the demo (budget raised from 3.5 to 4.0 KB in both, the measurement plus 10 percent), all own paths 40.58 KB (budget 41 KB), the zero-config first MP4 38.75 KB (budget 39 KB) and the standalone worker 35.77 KB (budget 36 KB).

- `npm run compare` scores `avgFps.declared` and `nominalFps` of a Matroska track without DefaultDuration exactly against ffprobe; they were not applicable. They stay not applicable in header mode, and a missing estimate after blocks were read is a mismatch. The library arms that return no such value count it as not provided (22 checks of mediabunny's idiomatic arm, 23 of its full scan). The own engine has 22 more exact checks on the committed fixtures (1924) and 22 fewer not applicable (65).
- The no-DefaultDuration warning of a Matroska track now says what happened to ffprobe's estimate: `no DefaultDuration: avg_frame_rate and r_frame_rate estimated like ffprobe from N video packets`, `... not reproduced (reason)` or, in header mode, `... come from the first packets, which header mode does not read`.
- The Matroska parser chunk grows by about 0.36 KB gzip (11.14 to 11.50 KB in the size matrix, budget 12.5 KB; 11.10 to 11.45 KB in the demo, budget 12.0 KB) for the CodecPrivate, the block hook and the call of the estimate, and a new lazy `rfps` chunk of 2.76 KB loads for a Matroska track without DefaultDuration. It is budgeted at 3.5 KB in the size matrix and in the demo, counts in all own paths (39.71 KB of 40 KB in the default configuration), and the demo has a row for the first Matroska file without DefaultDuration (102.06 KB of 105.5 KB). The one-file workers grow to 37.93 KB for the first MP4 (budget 38.5 KB) and the standalone worker to 34.96 KB (budget 35.5 KB); the lazy totals stay within their budgets. The critical path code did not change.
- `isAbortError` and `isTimeoutError` check the name and the code instead of `instanceof`, so a `ProbeError` from another copy of the package counts too. They moved to their own module, which keeps the critical path at 0.67 KB with the stub's load error added.
- When the last worker of a pool fails to load, the queued jobs reject at once, a transient network error included; before, each queued job started a new worker. The next call retries. A worker that throws at the top level, before its first reply, counts as a load failure too.
- `compare` reports a load failure of an engine as `crashed`, as before; `error.reason` now tells it apart from a crash.
- The mediabunny engine is verified with mediabunny 1.62.1: `MEDIABUNNY_VERSION` and `result.mediabunny.version` read `'1.62.1'`. Its results on the corpus did not change, and the peer range stays `^1.62.0`.
- A file smaller than 465,536 bytes, the 64 KiB head window plus `perReadMs x bytesPerMs` of the cost model, is read whole in its first read, so a small MP4 with the moov at the end takes 1 read instead of 2. Every committed fixture takes 1 read (the median was 2) and every result is unchanged; `io.bytesRead` of such a file is its size. `costModel: { perReadMs: 0 }` keeps the first read at `readAhead.head`, and the single read is at most 1 MiB (or `readAhead.head` when that is larger) whatever the cost model, so a cost model tuned for a fast disk cannot read a large file into memory at once ([parser options](docs/api.md#wireoptions-parser-options)).
- The probe client grows by 0.24 KB gzip and the own worker entry by 0.10 KB (0.03 KB for the load reason, 0.07 KB for the single read and its cap), so the first MP4 loads 23.60 KB instead of 23.26 KB in the default configuration. The package's size promise is the consumer size matrix: every configuration passes its budgets, and the critical path is 0.66 to 0.67 KB, as in 0.1.0. Its code did not change in this cycle; its gzip size moves by a few bytes with the hashed name of the probe client chunk it imports, which changes with every change to the worker code (between 663 and 668 bytes in this cycle).
- Demo: the Compare panel heads the mp4box and mediabunny columns "mp4box (tuned adapter)" and "mediabunny (tuned adapter)": they run this package's adapters over each library, not the libraries' own recipes.
- `readme-tables` decides whether the Chrome timings were measured on the current build by a content hash of each chunk the bench fetched (hashed import names reduced to their stems), recorded by `npm run bench` and `report/size.json`, instead of the chunk stem and byte size, which two different builds can share. A bench report without hashes counts as current only when every fetched file name is in the current build.
- `readme-tables` names the bench browser from the headless mode the run recorded: "Chrome headless shell" for `chrome-headless-shell`, "Chrome N (headless=new)" for the new headless mode, and "mode not recorded" for a report without one. Before, every `HeadlessChrome` user agent read as the headless shell, which is wrong for the new headless mode.
- Demo: the sample file loader is a lazy chunk. The demo budgets are the measurement plus 3 percent, rounded up to 0.5 KB: main 77.0 KB (was 75.0 KB), initial 83.0 KB (was 85.0 KB), first MP4 103.0 KB (was 100.0 KB; it measured 99,995 bytes when the budgets were set), first VFR MP4 105.0 KB (101.5 KB in 0.1.0; it measured 101.84 KB when set, with the load reason, the reload banner with its deploy check and the panel retry) and first Matroska 102.0 KB (was 100.0 KB). They cover the demo page only and left 2.51 to 3.16 KB of headroom per row when set, so a smaller demo regression passes the check. The size promise of the package is the consumer size matrix, whose budgets did not change.

### Not yet

- Demo: no prewarm before the first file. Prewarming on load or on idle would move about 19.5 KB of lazy loads onto every page view, and a tab that sits unused across a deploy still needs the reload banner.

## 0.1.0 - 2026-10-24

First release; not on npm yet (`"private": true`).

### Added

- Frame rate (an exact rational and ffprobe's `avg_frame_rate`), nominal, minimum and maximum FPS, frame counts, duration, codec, size and rotation per video track, a VFR flag and a rate profile, read from MP4, MOV (fragmented included), WebM and Matroska headers in a module worker, without decoding. Values carry provenance tags; file problems are `result.error`.
- Entries: `.` and `./lazy` with the own worker, `./client` and `./client/lazy` for a host worker, the `./mp4box`, `./mediabunny` and `./rvfc` engines, `./worker-runtime` and `./engines/*` for a custom worker, and `./standalone/own.worker.js` ([API](docs/api.md)).
- `analyze` with `engine` and `fallback`, `tryAnalyze`, `compare` (experimental), `prewarm`, `dispose`, `destroy`, `summarize`, `ProbeError`, the in-thread `analyze` for Node, and worker protocol v1.
- Chrome and Edge 94, Firefox 114, Safari 15.4 (derived floors); CI runs Chromium, Firefox and WebKit.
- 0.67 KB gzip on the critical path of a Vite 8.3.5 host; the first MP4 loads 23.26 KB lazily with `worker: { format: 'es' }`.
- 0 mismatches against ffprobe 8.1.1 on the 111 committed fixtures.

### Known limitations

- Zero-config Vite (iife workers) loads 34.77 KB for the first MP4: the probe client and one 32.11 KB worker file with both parsers.
- A regular cadence such as 2:3 pulldown is VFR, but its rate profile reads as Steady.
- rVFC needs playback: a visible foreground tab, a playable codec and seconds per file.
- Files above 2^53 bytes, `cmov` headers and a moov above 256 MiB are rejected as error results.
- In `auto` mode a large Matroska file gets a sampled probe unless the exact scan is predicted to take at most 150 ms.
- Only Vite 8 is verified; the other bundlers are documented, not tested ([bundlers](docs/bundlers.md)).

### Not yet

- React entry (0.2.0), bundler matrix and peers job (0.3.0), npm publishing (1.0.0).
