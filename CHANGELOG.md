## Unreleased

These changes go into 0.2.0, a minor release under the [0.x policy](docs/api.md#versioning): `ProbeError.reason` is a new optional field, and a lazy stub whose probe client fails to load rejects with a `ProbeError` instead of the browser's import error, which code that tested that error has to follow (see Fixed).

### Added

- `video-fps-probe/react`: `VideoFpsProvider`, `useVideoFps(file, options)` with `{ status, result, summary, error, progress, cancel, retry }`, `useVideoFpsProbe()` and `usePrewarmVideoFps()`, for React 18 and 19 (an optional peer, `>=18`). The provider takes the probe and is required: there is no default probe, so the entry never reaches the own worker literal, and a hook outside a provider throws `ProbeError('engine-not-registered')` with `wrap in VideoFpsProvider`. The state comes from a framework-free store, unit-tested in Node, which caches results per provider in a `WeakMap` by Blob, then by engine and options, runs one analysis through the double effects of `StrictMode`, starts nothing during a server render, aborts a pending analysis when its last component unmounts and starts it again when a component subscribes again (a memoized component that `<Activity>` hides and shows again included), and fetches `summarize` as a lazy chunk in parallel with the first analysis. Only that chunk failing to load gives `worker-failed` with `reason: 'load'`; a rejection that is not a `ProbeError`, an `analyze` of a custom probe that throws synchronously or a summary that throws gives `reason: 'crash'` (a thrown `ProbeError` is kept), and every failure settles to the error state instead of throwing from `subscribe`. `dist/react/index.js` starts with `'use client'`; `check-dist` requires that and fails on a `react` or `react-dom` import outside `dist/react/` ([React](docs/api.md#react)). The cap of the unpacked package moves from 460 to 470 KB for the entry.
- Two consumer fixtures for `video-fps-probe/react`, `react` (React 19.3.1) and `react18` (React 18.3.1, installed with the tarball into `react18/` of the consumers directory and aliased in its Vite config; both installs run with `--strict-peer-deps`, so a peer range that React 19 or 18 does not satisfy fails `consumers:setup`), in the size matrix and the consumer smoke test. The React entry adds 1.18 KB gzip to the critical path, 1.64 KB with the lazy stub (budgets 1.5 and 2 KB; design estimate 1.5 KB), and the summary module 0.43 KB lazily (budget 0.5 KB), so the first MP4 of a React host also loads that module (24.03 KB, budget 25 KB); React itself is not counted. The smoke test renders `useVideoFps` for three files under `vite build` and `vite dev`, compares each result and summary with Node's, and checks that each file is analyzed once and never aborted, through the double effects of `StrictMode` in dev, and not again after a re-render or a remount. With React 19 it also hides a memoized component in `<Activity>` while its analysis is held, and checks that the analysis is aborted and runs again when the component is shown.

- `video-fps-probe/check`: `check(result, rules)` judges a result against upload limits in the calling thread, before the upload round trip. The rules are JSON: `fps` (`min`, `max`, `exact`, `oneOf`, and `source`: the presented average by default, or ffprobe's average, the nominal or the dominant rate; on a constant track with 1 ms timestamps the default judges the nominal rate, since the rounded span puts the average a little off it and a 60 fps WebM would otherwise break `max: 60`, and the duration of such a track is its frames over that rate), `duration`, `frameSize`, the stored frame size after rotation without the sample aspect ratio (`minWidth` to `maxLongSide`; named `frameSize`, not `display`, because a pasp box or a Matroska DisplayWidth is not applied), `aspectRatio` and `pixels` of that size, `fileSize`, `containers`, `codecs`, `audio` (`'required'` or `'forbidden'`, unknown for an rvfc result, whose engine counts no audio tracks), and `vfr` and `uneven` policies (`'allow'`, `'warn'` or `'reject'`; a missing `isVfr` or a rate profile without `uneven` is unknown, not constant or even). Bounds are inclusive and compared as exact rationals, so 23.976 fps (`24000/1001`) is below a minimum of 24 and 59.94 meets a maximum of 60. A frame rate bound written as the decimal 23.976, 29.97, 47.952, 59.94 or 119.88 holds for the decimal and for its x/1001 rate, so `max: 29.97` accepts `30000/1001` and `exact: 23.976` matches `24000/1001`. With the default source, on a constant track on 1 ms ticks a frame rate bound also holds within the resolution of the timestamps, so `exact: '60000/1001'` matches the `19001/317` that the DefaultDuration of a 59.94 fps WebM stores, and `exact: 60` does not. A violation message prints the actual rate or duration with enough decimals to differ from the bound it breaks. The report has a verdict (`pass`, `warn`, `fail` or `unknown`), the violations with the rule, severity, expected and actual values and a message, and a `suggestedFps` with a plain reason when the rate or its evenness breaks a rule: a rate every bound of the `fps` rule allows, named exactly in the reason, or `value: null` with a reason when no rate meets every bound (an empty `oneOf`, a `min` above the `max`, an `exact` rate outside them). A missing result, a result with an error or without `videoTracks` (a partial or older JSON) and a missing field give `unknown`, never an exception, so an upload flow can fail open; such a result still fails a file size or a container it breaks. Malformed JSON gives `unknown` too, never an exception, with a message that says what is missing: a result that is not an object, null or non-object entries of `videoTracks`, tracks without a `trackId`, a `primaryTrackId` that is missing or matches no track, and fields of the wrong type. A rule value of the wrong type or outside its list, such as `audio: 'require'`, a list where an object or a single bound is expected, and a key that is not a rule, such as `fps.mxa`, throw a `TypeError` naming the rule, so a typo cannot turn a limit off. The entry imports no module at run time, which `check-dist` enforces ([Check](docs/api.md#check)).
- A `check` consumer fixture imports `video-fps-probe/check` statically next to `video-fps-probe/lazy`. In the size matrix the entry adds 3.60 KB gzip to the critical path (4.16 KB with the stub, budgets 4.0 and 4.5 KB) and nothing lazily; the 0.67 KB critical path of the default configuration does not change. The design estimated 0.8 to 1.5 KB; the 1 ms tick rule, the rule validation, the NTSC decimals and the suggestions that respect every bound account for the rest. A consumer test in every browser checks four committed files against one set of rules in the built and the dev app and compares each report with Node's from the same tarball.
- `video-fps-probe/presets`: the published input limits of six video generation APIs for a reference or source video, as `check()` rules, each with `sourceUrl`, `sourceKind` (`'official'` or `'gateway'`), `verifiedAt` and a `note`: `klingO1ReferenceVideo`, `klingMotionControl` (Motion Control 3.0), `runwayAleph2`, `veoExtend` (Veo 3.1), `wan26ReferenceToVideoFal` and `seedance2ReferenceVideo` (from the fal and EvoLink gateways, which serve another company's model, so their violations are warnings). Every number was read again from its source on 2026-10-25; limits a page leaves ambiguous or does not publish are left out and named in the note, such as the 4k size of Veo, the input resolution of Aleph and the codecs of Kling. No page says whether its MB is decimal or binary, so a size limit holds the larger reading, MiB, and the note names it: a file reported over it is over under either reading. Each preset is a named export of a module with no imports, so a host bundles only the presets it imports, and it is typed read-only and frozen at every level, since every importer shares it: writing to a preset throws a `TypeError` in strict mode. The freezing call of each preset is annotated `/*#__PURE__*/`, so bundlers still drop the presets a host does not import. The preset tests require a source, a kind, a date and a note, and warn without failing when a preset was verified more than 90 days ago ([Presets](docs/api.md#presets)).
- A `preset` consumer fixture imports `klingO1ReferenceVideo` next to `check` and the lazy stub. The preset adds 0.46 KB gzip to the critical path with its freezing helper (4.51 KB in all, budgets 0.5 and 5.0 KB); the six presets together are about 1.5 KB, so the 0.5 KB budget also fails a build that stops tree-shaking them, and a consumer test finds only that preset's source in the build. The browser reports equal Node's in every browser, in the built and the dev app.

- `ProbeError.reason` on every `worker-failed` the probe raises: `'load'` when code it needs did not load (the worker script, a chunk a worker loads for an engine or warms, a main-thread chunk, the probe client of a lazy stub, or `new Worker()` threw), `'crash'` when it failed after loading. The predictions were committed before the first run; the own prediction failed on that run with one mismatch caused by a wrong manifest note, and the results, that correction included, are in [the benchmarks](docs/benchmarks.md#late-rate-changes-tier-l).
- Twelve browser recordings (Tier R, 869 KiB together): real MediaRecorder output of headless Chromium 156, WebM VP8, VP9 and AV1, Matroska H.264, and fragmented MP4 with H.264 and VP9, each in one piece and with a 250 ms timeslice, recorded by the new `scripts/fixtures/record-mediarecorder.mjs` and committed as recorded (CC0, [provenance](fixtures/README.md#browser-recordings-tier-r)). The own parsers have no mismatch on them, and the rate profile recovers the recorded pacing. The eight WebM and Matroska files store no last frame duration: ffprobe estimates it from its rate, the own parsers take the median interval. Their measured averages therefore differ from ffprobe's packet average by definition, by design and not by a measurement error: `avgFps` is the presented frames over the presentation span, and ffprobe parity is `avgFpsFfprobe`. `npm run compare` scores that difference within tolerance and labels it a definition difference by design, only when the average is exactly the frames over the timestamp span plus one median interval, so a last frame of any other length, zero included, is still a mismatch. The same rule covers `vfr_concat_10_30_60.webm`, a per-file known deviation before; those 9 checks are 9 of the 13 own within-tolerance verdicts, and the own deviation files are empty. WebKit on Windows has no MediaRecorder, and Firefox recordings wait for the manual `record-firefox` workflow.
- `npm run compare` runs the libraries in five arms: `mp4box-idiomatic` (the mp4box.js README recipe and its own fields), `mediabunny-idiomatic` (the mediabunny README metadata recipe, `input.computeDuration()` included, and `computeFrameRateMetrics()` with its defaults), `mediabunny-full` (`targetPacketCount: Infinity`, with its `probedPacketCount` as the frame count), and `mp4box-tuned` and `mediabunny-tuned`, this package's adapters, which were the `mp4box` and `mediabunny` engines (both names still select them). Each mismatch of an arm is classified as wrong, definition differs (the definition the library documents or implements for the field, evaluated on the file; each arm is checked against its own definitions only, mediabunny's `computeFrameRateMetrics()` replayed on the reference timestamps, `getDurationFromMetadata()` on the media headers, and its end timestamps with the zero duration it gives a Matroska last frame whose duration the file does not store), unverified (that definition cannot be evaluated on the file, or the value only equals a quantity the arm does not use, so it is counted neither as wrong nor as a definition difference), not provided or unsupported container, and [the accuracy section](docs/benchmarks.md#accuracy-vs-ffprobe) lists where the libraries win: every check where an arm is exact or within tolerance and the own parsers are not, over all fixtures with the large local files (marked when the arm's VFR flag on that track is wrong, or when the own parsers report the same value under a not applicable verdict), and the files an arm reads with fewer bytes or reads or in less time, counted on the files that both it and the own parsers open.

Reload to continue.", with a Reload button, and the files read "Not analyzed."; if not, each file reads `Worker could not be loaded:` with the error.
- `avgFpsFfprobe` and `rFpsFfprobe` for a Matroska or WebM track without DefaultDuration: the `avg_frame_rate` and `r_frame_rate` that ffprobe 8.1.1 estimates from the first packets, reproduced bit for bit in `matroskaMode` `probe`, `exact` and `auto` (`header` mode reads no block and leaves both null). It covers browser MediaRecorder recordings, which never store a DefaultDuration: the 12 committed files without one, 8 Chromium recordings among them, now give ffprobe's strings (60/1 or 60000/1001 on the recordings, `0/0` where ffprobe prints that), and 503 more Matroska files without one, generated from the recordings with random timing and late Opus audio, matched ffprobe on both strings. The code is a lazy chunk, `core/rfps.js` (3.60 KB gzip in the size matrix), which the Matroska parser loads only for such a track and which reads only the first packets: 41 video packets of a Chromium recording, 48 for H.264. Outside the reproduced cases (other codecs, more than one video track, tracks other than Opus, laced blocks, H.264 that is not Baseline, signals timing or reordering, or whose headers do not fix the decoder delay at 0 or that does not start with an IDR, AV1 with timing info, damaged first Clusters) both stay null and the warning names the reason ([implementation notes](docs/implementation-notes.md#ffprobe-frame-rates-without-defaultduration-020)).

### Fixed

- `npm run compare` scored `avgFps.declared` of a Matroska track without DefaultDuration exact when ffprobe printed `0/0` and the engine reported no estimate after reading blocks, as if both had said the same. A missing estimate after a block read is a mismatch there too, its detail names ffprobe's `0/0`, and header mode stays not applicable with its reason. The own engine prints `0/0` itself, so its results do not change; mediabunny's idiomatic arm and its full scan get 2 more not-provided checks each (`vfr_concat_10_30_60.webm`, `vfr_two_phase_5_200.webm`). The self-test oracle now reports ffprobe's `0/0` the way the own estimate does.

- `avgFpsFfprobe` and `rFpsFfprobe` of a Baseline H.264 track in Matroska without DefaultDuration could be an estimate that assumes no decoder delay where ffprobe's decoder raises its reorder delay to 1: without a VUI `bitstream_restriction`, FFmpeg does that when the picture order count of a decoded frame steps by more than 2 or goes back, and its strings then differ when the blocks carry durations. The parser now reads the PPS and the slice headers of the first 7 packets, the ones the decoder sees, and reports no estimate, with the reason in the warning, for a POC step other than 1 or 2, a `frame_num` gap, `pic_order_cnt_type` 1, field coding, a bottom field POC offset or a slice header it cannot read. With or without `bitstream_restriction`, it also reports none when the first packet is not an IDR: FFmpeg outputs no frame for a first I slice that is not one, so its dts start one packet later than the estimate assumes, and on 240 Baseline files built that way 5 of 166 estimates differed from ffprobe. With a `bitstream_restriction` that fixes the delay at 0 the parser used to skip the slice headers; FFmpeg then outputs no picture whose POC goes back below the last one it output (`h264_select_output_frame` with `has_b_frames` 0), which starts its dts a packet later too, so the parser now reads them there as well and reports no estimate for a POC that goes back, a `frame_num` gap, `pic_order_cnt_type` 1 or field coding; a step forward of any size keeps the estimate. That check adds 0.04 KB gzip to the `rfps` chunk. A Chromium recording, whose SPS has `bitstream_restriction` with no reordering, is unaffected, and so is every committed fixture. The SPS in CodecPrivate or in the first block is now read only up to its own length. The `rfps` chunk grows by 0.63 KB gzip for it, and so do all own paths, the one-file workers, which inline the chunk, and the emitted lazy totals, which carry it twice, in the worker and in the main-thread copy. The critical path and the first MP4 of the default configuration did not change. The cap of the unpacked package moved from 450 to 460 KB ([implementation notes](docs/implementation-notes.md#ffprobe-frame-rates-without-defaultduration-020)).

- The mp4box engine (`video-fps-probe/mp4box`, the tuned adapter) ended a fragmented track at the sum of its trun sample durations. It now follows the tfdt timeline, as ffprobe and the own parser do: a fragment with a tfdt starts there, and the track ends at the latest fragment end. Chrome MediaRecorder fMP4, whose fragments end with a placeholder sample duration of 999 ticks, now gets ffprobe's track and format duration (4.524533 s instead of 4.557667 s on `rec_chromium_h264.mp4`).
- A worker script that failed to load, for example a 404 in a tab opened before a redeploy, was reported as a crash: a bare `worker failed`, or `Uncaught SyntaxError: Unexpected token '<'` when Chromium parsed the 404 page as a classic worker. Any worker `error` event before the worker's first reply now rejects with `reason: 'load'`, the message `worker script failed to load or parse; the app may have been redeployed`, followed by the event's message when it has one, and the error event as `cause`. An `error` event after the first reply stays `reason: 'crash'`. While another worker of the pool is alive, the job waits for it and no further worker starts until the next call; when the failed worker was the last one, its job and the queued jobs reject once instead of fetching the script again for every queued file. The next call loads the worker again.
- A lazy stub whose probe client chunk failed to load rejected with the browser's import error as it was. It now rejects with `ProbeError('worker-failed')`, `reason: 'load'` and that error as `cause`, so every rejection of a probe or a stub is a `ProbeError`; a `ProbeError` of the factory is passed through. Code that read a stub rejection without `instanceof ProbeError` as a load failure should read `e.reason === 'load'`.
- A failed `warm` replied without `reason`, so a prewarm whose engine or parser chunk did not load was tagged `crash`. It now carries `reason: 'load'`.
- Release: the version step carried the intro of the Unreleased section ("These changes go into ...") into the released section. It now drops the text before the first `###` heading and prints it. `preversion` stopped with a bare git error when `user.name` or `user.email` was missing, and went on when one was set to an empty value; it now fails in both cases, before the gates, and names both values ([Releasing](docs/releasing.md)).
- `npm run compare` took the absence of a Matroska DefaultDuration, which makes the declared average not applicable, from a regex over the fixture's manifest note, so editing a note could turn a gating mismatch into n/a. It now scans the Tracks element of the file, and a note that says the element is absent while the file has it stops the run with exit code 2.
- `npm run compare` classified the mediabunny tuned adapter's average of `rec_chromium_vp9.mp4` and `rec_chromium_vp9_sliced.mp4` as wrong, although it is the arm's definition, `computePacketStats().averagePacketRate`: the packets over the span from the first timestamp to the largest timestamp plus duration. The span ends at the stored duration of the last sample, a 999-tick placeholder where ffprobe gives that packet 500 ticks. The layout scan now reads that stored duration from the file (the last trun entry, or the last stts delta), and the two checks count as definition differs.

### Changed

- `auto` counts the walk that probe mode reads for the ffprobe frame rate estimate of a Matroska track without DefaultDuration (predicted from the sampled block density: 48 video packets, at most 5,000,000 bytes) and picks exact when the exact plan is within `exactBudgetMs` plus that walk, which probe mode reads anyway; the warning of a skipped exact scan names it. On a 149.1 MB 720p60 VP8 WebM without DefaultDuration the walk costs probe mode 9 reads and 131.5 KB (predicted 10 ms), and auto keeps probe (exact predicted 415 ms). In `exact` mode, and in `auto` when it picks exact, the ffprobe frame rate estimate of a Matroska track without DefaultDuration takes its blocks from the block walk of the exact scan instead of walking the first Clusters itself before it, and copies the packet heads it needs from the scanner's buffer. The first Clusters are read once, so the exact plan of `auto` now covers the estimate, except a packet head the buffer did not hold, which the estimate reads again (at most 1 KiB, up to 7 for H.264) and the plan does not count: a 20 MB 720p60 VP8 WebM without DefaultDuration takes 20 reads instead of 26 for the same 19.9 MB (median 30.5 to 29.3 ms over three interleaved runs in Node 24 from a local SSD), with the same strings, frames and warnings. `probe` mode keeps a walk of its own, because the probe reads only 32 blocks of the first Cluster. The estimate and the Matroska parser grow by 0.23 KB gzip for it.

- `npm run compare` scores `avgFps.declared` and `nominalFps` of a Matroska track without DefaultDuration exactly against ffprobe; they were not applicable. They stay not applicable in header mode, and a missing estimate after blocks were read is a mismatch. The library arms that return no such value count it as not provided (22 checks of mediabunny's idiomatic arm, 23 of its full scan). The own engine has 22 more exact checks on the committed fixtures (1924) and 22 fewer not applicable (65).
- The no-DefaultDuration warning of a Matroska track now says what happened to ffprobe's estimate: `no DefaultDuration: avg_frame_rate and r_frame_rate estimated like ffprobe from N video packets`, `... not reproduced (reason)` or, in header mode, `... come from the first packets, which header mode does not read`.
- The Matroska parser chunk grows by about 0.36 KB gzip for the CodecPrivate, the block hook and the call of the estimate, and a new lazy `rfps` chunk loads for a Matroska track without DefaultDuration. Both count in all own paths, the one-file workers inline both, and the demo has a row for the first Matroska file without DefaultDuration. The critical path code did not change. The sizes and budgets are in the "Sizes at 0.2.0" entry below.
- `isAbortError` and `isTimeoutError` check the name and the code instead of `instanceof`, so a `ProbeError` from another copy of the package counts too. They moved to their own module, which keeps the critical path at 0.67 KB with the stub's load error added.
- When the last worker of a pool fails to load, the queued jobs reject at once, a transient network error included; before, each queued job started a new worker. The next call retries. A worker that throws at the top level, before its first reply, counts as a load failure too.
- `compare` reports a load failure of an engine as `crashed`, as before; `error.reason` now tells it apart from a crash.
- The mediabunny engine is verified with mediabunny 1.62.1: `MEDIABUNNY_VERSION` and `result.mediabunny.version` read `'1.62.1'`. Its results on the corpus did not change, and the peer range stays `^1.62.0`.
- A file smaller than 465,536 bytes, the 64 KiB head window plus `perReadMs x bytesPerMs` of the cost model, is read whole in its first read, so a small MP4 with the moov at the end takes 1 read instead of 2. Every committed fixture takes 1 read (the median was 2) and every result is unchanged; `io.bytesRead` of such a file is its size. `costModel: { perReadMs: 0 }` keeps the first read at `readAhead.head`, and the single read is at most 1 MiB (or `readAhead.head` when that is larger) whatever the cost model, so a cost model tuned for a fast disk cannot read a large file into memory at once ([parser options](docs/api.md#wireoptions-parser-options)).
- The probe client grows by 0.24 KB gzip and the own worker entry by 0.10 KB (0.03 KB for the load reason, 0.07 KB for the single read and its cap), so the first MP4 of the default configuration grows from the 23.26 KB of 0.1.0 to 23.59 KB with the rest of this release. The package's size promise is the consumer size matrix: every configuration passes its budgets, and the critical path is 0.66 to 0.67 KB, as in 0.1.0. Its code did not change in this cycle; its gzip size moves by a few bytes with the hashed name of the probe client chunk it imports, which changes with every change to the worker code (between 663 and 668 bytes in this cycle).
- Demo: the Compare panel heads the mp4box and mediabunny columns "mp4box (tuned adapter)" and "mediabunny (tuned adapter)": they run this package's adapters over each library, not the libraries' own recipes.
- `readme-tables` decides whether the Chrome timings were measured on the current build by a content hash of each chunk the bench fetched (hashed import names reduced to their stems), recorded by `npm run bench` and `report/size.json`, instead of the chunk stem and byte size, which two different builds can share. A bench report without hashes counts as current only when every fetched file name is in the current build.
- `readme-tables` names the bench browser from the headless mode the run recorded: "Chrome headless shell" for `chrome-headless-shell`, "Chrome N (headless=new)" for the new headless mode, and "mode not recorded" for a report without one. ## 0.1.0 - 2026-10-24

First release; not on npm yet (`"private": true`).

### Added

- Frame rate (an exact rational and ffprobe's `avg_frame_rate`), nominal, minimum and maximum FPS, frame counts, duration, codec, size and rotation per video track, a VFR flag and a rate profile, read from MP4, MOV (fragmented included), WebM and Matroska headers in a module worker, without decoding. Values carry provenance tags; file problems are `result.error`.
- Entries: `.` and `./lazy` with the own worker, `./client` and `./client/lazy` for a host worker, the `./mp4box`, `./mediabunny` and `./rvfc` engines, `./worker-runtime` and `./engines/*` for a custom worker, and `./standalone/own.worker.js` ([API](docs/api.md)).
- `analyze` with `engine` and `fallback`, `tryAnalyze`, `compare` (experimental), `prewarm`, `dispose`, `destroy`, `summarize`, `ProbeError`, the in-thread `analyze` for Node, and worker protocol v1.
- Chrome and Edge 94, Firefox 114, Safari 15.4 (derived floors); CI runs Chromium, Firefox and WebKit.
- 0.67 KB gzip on the critical path of a Vite 8.3.5 host; the first MP4 loads 23.26 KB lazily with `worker: { format: 'es' }`.
- 0 mismatches against ffprobe 8.1.1 on the 111 committed fixtures.

### Known limitations

- Zero-config Vite (iife workers) loads 34.77 KB for the first MP4: the probe client and one 32.11 KB worker file with both parsers.
- A regular cadence such as 2:3 pulldown is VFR, but its rate profile reads as Steady.
- rVFC needs playback: a visible foreground tab, a playable codec and seconds per file.
- Files above 2^53 bytes, `cmov` headers and a moov above 256 MiB are rejected as error results.
- In `auto` mode a large Matroska file gets a sampled probe unless the exact scan is predicted to take at most 150 ms.
- Only Vite 8 is verified; the other bundlers are documented, not tested ([bundlers](docs/bundlers.md)).

- React entry (0.2.0), bundler matrix and peers job (0.3.0), npm publishing (1.0.0).
